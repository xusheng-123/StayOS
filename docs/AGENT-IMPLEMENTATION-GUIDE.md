# StayOS 多智能体连续开发执行手册

编制日期：2026-10-31。适用仓库：StayOS。本文是后续智能体执行增量开发的统一入口，所有路径相对仓库根目录。

## 1. 使用方式、授权与完成标准

### 1.1 本文的作用

本文同时规定版本顺序、技术选择、界面风格、业务契约、实现步骤、验收方式和多智能体交接。后续不要重新选择框架、重新设计工作台或凭个人偏好改变版本顺序。产品取舍与官方对比见 [VERSION-ROADMAP.md](VERSION-ROADMAP.md)，本地 V1.0 基线见 [V1-CLOSURE.md](V1-CLOSURE.md)，真实上线事项见 [V1-RELEASE-CHECKLIST.md](V1-RELEASE-CHECKLIST.md)。

编写本文不等于已经开始后续版本开发。用户以后明确要求“按本手册连续开发”时，在该次授权的版本范围内连续执行，不在每个文件、常规实现选择或每个已授权小版本结束后反复询问是否继续。用户只指定某一版时，只实现该版；不要借本手册扩大授权。

当前 V1.0 原始规则继续有效。只有进入对应新版本时，才按本文增量扩展并同步 PRD、DATABASE、API；不要把后续设计写成已经上线的能力。最新用户明确指令优先于本文；实现与旧文档不一致时，先核实代码及该版的已批准规则，不能随意挑选对自己方便的一方。

旧 DEVELOPMENT.md 中“技术建议待选”“遇到任何未决事项暂停整个任务”的通用描述，后续以本手册的已核对技术栈、配置要求和连续执行规则为准；旧版业务约束只有在本文明确指定的对应新版中才扩展。

### 1.2 后续智能体开工必读顺序

1. 本文全部内容，尤其第 2、4、5、6、19 节与当前版本章节。
2. 本文第 20 节进度表及第 21 节最近交接记录，确认上次实际停在哪一步。
3. `git status --short`、`git diff --stat`，保留全部已有修改；HEAD 不能代表未提交工作树。
4. 当前版本涉及的 PRD、DATABASE、API、对应业务说明与源码；不要求无差别重读全部历史报告。
5. 当前版本已有测试、最近测试日志和迁移文件最大编号，再决定下一步。

发现已有部分实现，先复核并续做；不得重建工程、覆盖前一智能体文件、重复建表或把未完成代码当作新需求重新做。

### 1.3 连续执行规则

- 遇到正常编译错误、测试失败、冲突或漏项，定位并修复后继续，不能仅给出计划就结束。
- 普通技术细节按本文默认值处理，记录决定，不反复询问用户。
- 酒店实际费率、营业时间、属地登记、供应商资格、外部凭据等事实不能编造。能用配置表达的，完成配置、校验与测试；未配置时明确拒绝相关操作，不把示例值带进真实业务。
- 一个外部集成受阻时，继续当前授权范围内不依赖它的工作，并留下准确阻塞信息。不得把依赖它的版本标为完成，也不得跳过必需前置版本直接开发下游。
- 条件版本默认 `DEFERRED`，不会阻塞主线；明确启用并验收后才加入依赖链。
- 不推送远程 Git、不真实部署、改开发数据库账号/密钥、安装常驻任务、上传备份、连接真实支付或发送外部消息。这些操作需要用户既有或新的具体授权；本地代码与测试继续推进。
- 每个版本通过完整验收（VERIFY）后，必须在 HANDOFF 阶段把本版全部代码、迁移、测试、文档和交付记录提交到本地 Git，提交说明沿用 `feat: 完成Vx.y…` 风格，使 Git 历史与第 20 节进度表一致。只提交、不推送；推送远程始终需要用户单独授权。版本中间过程不要求逐文件提交，也不得用 reset/强制覆盖破坏既有历史或用户修改。
- 时间或上下文不足时先更新交接记录，保留可定位的现场；后续从记录恢复，不重复已完成验收。不得把中断、等待或工具退出写成成功。

### 1.4 一版怎样才算完成

必须同时具备：真实可操作页面、接口、服务端权限、数据库约束、事务/并发保护、幂等、历史与审计、明确失败处理、相关自动化测试、界面核对、增量文档、最终同批完整回归与产物验证、版本 Git 提交。

`VERIFIED_LOCAL` 表示本地验收通过；`DEPLOYED`、`LIVE_ACCEPTED` 是另外的部署及现场状态。界面截图、Mock、编译成功、定向通过、旧报告或“后端已写好”均不单独构成整版完成。

### 2.2 所有版本保留的约束

1. 当前实际占用来自未结束的 `stay_room_segments`；同一房间、同一入住都至多有一个有效使用段。
2. 可入住统一经 `RoomEligibility` 判断：档案启用、无人占用、必要清洁完成、无未完成离房清洁、无严重异常阻止及人工维修停用。不要复制出另一套判断。
3. 清洁、维修、占用分别表达。清洁完成不能自动解除维修；异常解决不能自动清洁；住中服务完成不能释放房间。
4. V1 退房结束入住并自动创建清洁任务，不表示已结清。V2 账务引入后仍保留状态分离，不能静默把原退房接口改成必须付款。
5. 换房保留入住 ID 和住客；结束旧使用段、新建使用段、原房置脏、建清洁任务、换房事实和成功审计共同提交。
6. 离房清洁仍为 `PENDING → IN_PROGRESS → COMPLETED`；仅当前执行人可开始/完成，分配与受控接管只允许主管/总经理；自主领取保持关闭。
7. `ADMIN` 不自动获得酒店业务权限；总经理不自动获得管理员权限；一人可拥有多个固定角色。
8. 历史和审计不可删除或随意覆盖。业务更正用显式变更事实，财务差错用调整/冲正，不能开放万能“撤销”或直接改表。
9. 真实操作时间由服务器生成，`TIMESTAMPTZ` 保存时刻；界面使用 `Asia/Shanghai`。营业日期与实际时间分字段保存。
10. 证件、电话保持 `GuestProtection` 的 AES-GCM 加密与掩码输出；不换密钥、不擅改密文格式，不把敏感输入写进日志、URL、审计文本或浏览器持久存储。

## 3. 固定技术栈与工程组织

### 3.1 版本基准

以下是编制时仓库实际版本，不是要求每次联网升级。开工以 `pom.xml`、`package.json`、`package-lock.json` 及现有 Compose 为准；普通功能开发保持锁定版本，不执行 `npm update` 或顺带升级整套依赖。

| 层 | 技术与基准 | 执行要求 |
| --- | --- | --- |
| 后端 | Java 21、Spring Boot 3.5.16、Spring MVC、Security、Validation | 一个 Maven 模块、一个应用进程 |
| 数据访问 | MyBatis-Plus 3.5.17，现有注解 Mapper/明确 SQL | 不引入 JPA、第二套 ORM 或通用 CRUD 框架 |
| 数据库 | PostgreSQL 17，Flyway | 真实 PostgreSQL 约束与事务；不用 H2 替代核心验收 |
| 前端 | Vue 3.5.44、TypeScript 5.9.3、Vue Router 4.6.4 | Composition API，`<script setup lang="ts">`，严格类型 |
| UI | Element Plus 2.14.7、现有 CSS | 复用工作台和组件，不引入第二套 UI/主题框架 |
| 构建 | Vite 8.3.4、vue-tsc 3.3.13 | 使用现有脚本与按路由懒加载 |
| Node | `^20.19.0 || >=22.12.0`，当前机器 Node 24 | 按锁文件 `npm ci`，不重写依赖树 |
| 测试 | JUnit 5、Spring Boot Test、AssertJ、Playwright 1.64.1 + Edge | 复用 JUnit 数据/账号夹具启动浏览器 |
| 本机工具 | PowerShell 7、Maven 3.9、Docker Desktop Linux 容器 | 复用 `scripts/env.ps1` 的用户目录工具发现 |
| 架构 | 模块化单体 + REST/JSON + 同源 Session | 不擅改 JWT、微服务、Redis、消息中间件或原生 App |

### 3.2 目录和实现落点

```text
backend/src/main/java/com/stayos/
  auth/                    身份、角色权限、业务操作人复核
  common/                  统一响应/错误、请求编号、就绪检查
  stay/{controller,service,mapper,dto}/
  room/{controller,service,mapper,dto,entity}/
  housekeeping/{controller,service,mapper,dto}/
  issue/                   现有异常模块，保持其实际组织
  operations/              现有运营待办
  audit/                   成功/失败/拒绝审计
  staff/                   员工管理
  handover/                V1.3 新增
  guestservice/            V1.4 条件新增
  billing/                 V2.0 新增
  cashier/                 V2.1 新增
  reservation/             V3.0 新增
  integration/             V4.0 起的供应商适配
  customer/                V5.0 新增
backend/src/main/resources/db/migration/
backend/src/test/java/com/stayos/
frontend/src/{api,components,composables,layouts,router,stores,types,views}/
frontend/e2e/
scripts/  deploy/  docs/
```

不要为每个简单类机械增加接口与实现类，不做无关目录重排。Controller 只做参数/身份接入，Service 执行业务事务，Mapper 做数据库访问，DTO 明确输入输出。跨模块通过 Service 协作，同一数据库业务尽量保持一个事务，不用 HTTP 调用自己。

前端继续使用 `ref/reactive/computed` 与现有小型 stores；不为普通新增页面引入 Pinia。API 类型放 `types/`，领域请求帮助函数放 `api/`，复用对话框放 `components/`，页面放 `views/`。

以 `style.css`、`rooms.css`、`stays.css` 和现有页面为准，不为每版换皮肤。

| 项目 | 固定值或规则 |
| --- | --- |
| 主题 | 深绿色侧栏、暖灰浅底、白色卡片，中文业务界面 |
| 主色 / 侧栏 / 页面底 / 正文 | `#23665a` / `#163e38` / `#f5f6f2` / `#263c38` |
| 卡片边框 / 次要文案 | `#e1e8df` / 复用 `.subtle` 的颜色与 14px 字号 |
| 字体 | `Inter,"Segoe UI","Microsoft YaHei",sans-serif`，不额外下载字体 |
| 圆角 | 按钮/控件 8px，内容卡片通常 10～12px |
| 布局 | 桌面侧栏 248px；顶部 80px；内容最大宽度 1500px；复用现有内边距 |
| 标题 | 主标题桌面 30px、手机 25px，页面小标题通常 16px；不大幅更改层级 |

页面骨架：`.rooms-page` → `.page-heading`（标题/说明 + `.heading-actions`）→ 筛选区 → 错误提示 → 内容卡片/列表 → 分页。复用 `.catalog-panel`、`.form-columns`、`.dialog-actions`、`.room-notes`。领域新增样式集中到该领域 CSS 或 scoped style；共享规则才进入公共 CSS，避免污染 `.el-*` 全局选择器。

### 4.2 交互标准

- 简单附属操作用现有 Element Plus 对话框；长表单/列表/日历用页面。续住、更正参照 `CheckoutDialog.vue`、`RoomChangeDialog.vue`，不要再做一套弹窗系统。
- 一屏有清晰主操作，破坏性或不可逆提交说明具体后果。按钮用“确认续住”“保存更正”等动词，不能只写“确定”。
- 表单有可访问 label，必填和长度规则前后端一致；保留输入错误，成功后刷新对应详情/待办。
- 各列表均提供加载、空数据、失败、重试及分页状态。服务端筛选分页，排序稳定；不把全部记录拉到浏览器再筛选。
- 写操作提交期间禁用重复操作；结果不确定时保留原幂等标识并支持查询/重试。关闭弹窗不能冒充撤销服务器操作。
- 手机按钮建议至少 44px 可点击高度；筛选与表单单列；长表格用卡片或限定容器滚动，不能撑宽整页。
- 继续使用中文业务文案；日志、类名、字段、状态码使用统一英文。产品页面不展示数据库锁、SQL、内部栈等实现细节。
- 金额由服务端计算并返回十进制字符串；前端仅格式化显示，不用浮点计算决定账务结果。
- 新 Element Plus 组件显式 import 或沿用 `main.ts` 的现有注册方式，不能假设未安装的自动导入插件会处理。

### 4.3 代码风格

保持 UTF-8、LF、现有命名习惯；新增较复杂 Java 代码使用清晰分行与局部方法，不压成一行，不做全仓格式化。TypeScript 不新增无理由 `any`、非空断言或重复请求封装；Vue 的 props、emits、响应类型明确。错误统一走 `ApiException`/`ApiErrors` 和 `ApiError`，不要吞异常或向用户返回原始 SQL/堆栈。

## 5. 数据、接口、权限和并发的统一契约

### 5.1 数据库迁移

- 开始前查看迁移最大编号；V1.2 当前为 V14，因此下一新增号可为 V15，但必须以开工时实际文件为准。
- 一个协调者分配迁移号，格式 `V{N}__snake_case_description.sql`；禁止多智能体各自猜下一个编号。
- 只新增迁移；不改已应用迁移、不 `flyway clean`、不删除历史来让约束通过。
- 表名 `snake_case`，主键 BIGINT identity，外键默认保护历史，明确 NOT NULL、CHECK、唯一约束及查询索引。列表按时间和 ID 稳定排序。
- 修改旧表采用兼容旧数据的迁移：先允许空/明确回填，再验证约束；不能虚构历史价格、手机号、接班确认或支付事实。
- 每次新表都复核 `deploy/runtime-grants.sql`：运行角色仅授业务所需权限，历史追加表不给 UPDATE/DELETE；受限账号专项测试同步增加。V1.2 如需更新 `guests` 的当前投影，显式授予该表必要 UPDATE，保留加密更正历史，不放开所有历史表。
- 业务操作 `@Transactional`；不能在同类自调用中假设代理事务生效。独立事务仅用于已有明确定义的失败审计等情形。

### 5.2 REST/JSON

现有成功响应为 `{"success":true,"code":null,"message":"操作成功","data":...}`。沿用 `ApiResponse`，HTTP 状态区分 400 参数、401 会话、403 权限、404 不存在、409 并发/状态冲突、503 暂时不可用。业务写操作使用明确动作 POST；GET 不改变业务事实。

所有本文列出的新接口/表/权限是实现契约建议名。开工先登记到 API/DATABASE，按实际既有命名作一次一致调整；合约固定后前后端不得各自改名。分页复用 `{items,total,page,pageSize}` 风格并核对当前类型，限制 pageSize；不为兼容“猜测客户端”同时维护多种形状。

### 5.3 幂等与结果不确定

1. 每次新意图一个 UUID `Idempotency-Key`，同一意图网络重试继续使用同一 key 和同一规范化 payload。
2. 幂等预留、业务事实、成功审计及结果指针在同一事务。沿用 24 小时语义：过期保留并拒绝自动复用，先查询历史再决定新操作。
3. `idempotency_requests.operation` 当前有 CHECK，新增操作必须同时扩展约束。需要新增结果 ID 时扩展对应 FK、Mapper result 字段、Service 结果分支；不把更正/交班 ID 硬塞进 `result_stay_id`。
4. 重放返回原操作回执，不用当前已变更详情冒充原始结果；仍复核当前操作人授权。
5. payload 有敏感字段时使用现有 HMAC 指纹，不使用可离线枚举的普通手机号/证件哈希。
6. sessionStorage 仅保存无敏感内容的操作标识/资源 ID。更正字段原文不持久化；刷新后无法恢复原敏感 payload 时先查询服务器回执/变更历史，不用同一 key 重建不同内容，也不直接新 key 重发。

需要跨刷新恢复敏感写操作时，增加按当前操作人范围查询的回执接口，例如 `GET /api/operation-receipts/{key}?operation=...`，或在该领域历史接口提供同等能力；回执只包含必要 ID/状态/掩码，不返回原请求正文。未知结果先查清，再允许明确的新意图，不能提供任何用户都能按 key 查询他人操作的公共接口。

### 5.4 权限与锁顺序

现有写链顺序为：幂等预留 → 操作人共享锁及当前权限/安全版本 → 入住 → 房间（ID 升序）→ 使用段 → 任务/业务事实。保持所有现有服务的相对顺序，不因新功能形成反向调用锁。

V2 引入客账时，在需要该锁的路径中安排在“入住之后、房间之前”。V3 引入预订与日期库存时，统一设计为“幂等 → 操作人 → 预订 → 日期库存（房型ID、日期升序）→ 入住 → 客账 → 房间 → 使用段 → 任务”。只锁需要的对象，但所有路径遵守同一相对顺序；预订转入住、续住、换房、退房的库存衔接必须一起复核。已创建对象用 ID 升序；新对象靠唯一约束/插入协议，不能锁一个不存在的行后假设已获得互斥。

涉及员工分配时复用既有员工有序锁逻辑，不另设相反的员工锁顺序。业务版本字段用于防止旧表单覆盖新结果，数据库锁/唯一约束用于保证并发正确；二者不可互相替代。

新权限加入 `RolePermissions`，前端路由、导航、按钮、后端入口与写事务守卫同步更新。只按固定角色映射权限；涉及退款、关账、敏感更正、渠道凭据等独立授权，不由“能看页面”自动推导能执行。

## 11. V2.0 账务基础：分小任务完成一套客账

### 11.1 边界和实施顺序

单店、人民币、人工登记酒店在外部已实际完成的收退款。先依次完成：**财务配置 → 房价快照/每日费用 → 额外服务 → 客账 → 收退款 → 结账明细**。账单、付款、入住三种状态独立，不接真实自动支付，不做财务总账、复杂团账、储值。

新权限建议：`billing:read`、`billing:charge`、`billing:receive` 默认前台/总经理；`billing:adjust`、`billing:refund`、`billing:configure` 默认总经理。ADMIN 不默认取得收银或退款权限，技术配置和业务价目维护明确区分。

### 11.2 金额、费率与时间规则

- Java `BigDecimal`、SQL `NUMERIC(18,2)`；API 金额十进制字符串，拒绝负数金额输入、NaN、超精度和溢出。流水金额为正，方向另列；调整可以使用明确的贷项类别。
- 首版仅明确的按晚房费，营业时区 `Asia/Shanghai`。退房时刻、计费日切、早到/晚退、提前退房、换房差价、续住定价作为可配置且有版本的酒店政策；未配置/确认时拒绝自动计费，不默认从测试示例推定真实规则。
- 可先完成“选择明确住宿日期与确认房价后手工入账”的闭环，每次确认展示日期、数量、单价、总额；V2.1 再做幂等日批。不能按浏览器时间或定时器偷偷累计房费。
- 价格表修改只影响将来选择；已确认的入住/预订/消费保存名称、计价单位、单价、币种及政策版本快照。
- 旧 V1 入住缺历史价格时标识 `PRICING_REQUIRED`/旧单接入状态，不倒推历史应收、不把缺数据当零元。接入时明确新费用生效日期，操作历史可追溯。

### 11.3 最小数据模型

| 表/领域 | 最小职责 |
| --- | --- |
| `billing_policies`、`rate_plans`、`room_rate_days` | 政策版本、房型价格、日期/入住价快照；历史价不可被当前价覆盖 |
| `service_catalog`、`service_orders`、`service_order_items` | 商品/服务价目、此次入住的请求和实际提供；取消未提供服务不计费 |
| `folios` | 一次入住的客账，单币种；旧单接入状态、账务状态和 version |
| `folio_charges` | 追加费用/贷项/冲正事实，关联入住、必要使用段、营业日、来源唯一键及原记录 |
| `payment_records` | 追加人工实收/实退，方式、用途、原流水、外部参考、经办人和时间；不是支付网关交易 |
| `folio_events` | 开账、结账、重新开放等有权限的状态变化，不删除历史费用/流水 |

费用与资金分别保存：`净应收 = 已入账费用 - 有效费用贷项`；`净实收 = 收款 - 退款`；`余额 = 净应收 - 净实收`，正数为未付、负数为预收剩余。押金/预收是一笔收款的用途，不再额外记一次收入。

普通退款不得超过原收款尚未退回金额及当前可退预收余额；费用更正先形成贷项再退相应款。其他导致欠款的特殊退款不在首版默认开放。相同外部参考的防重复规则按支付方式确定，不能假定所有现金收据有全局唯一单号。按客账加锁，数据库唯一键、额度和幂等共同防止并发超退。

例：2 晚 × 200 + 服务 30 = 应收 430；外部实际收款 500 后登记一次，退 70 后登记一次，净实收 430、余额 0。该例只验算账务，不代表系统自动扣款退款。

### 11.4 接口、前端与服务接点

- `/api/billing/policies`、`/rate-plans`、`/service-catalog` 做受控维护；不开放任意金额 SQL 式改写。
- `/api/stays/{id}/folio` 查询/受控建账；`/api/folios/{id}/charges`、`/payments`、`/refunds`、`/adjustments`、`/close` 为明确动作，全部权限、版本、幂等及审计。
- `/api/stays/{id}/service-orders` 创建消费请求，`/api/service-orders/{id}/fulfill`、`/cancel` 明确实际提供后才形成唯一费用来源，避免重复履约计费。
- 新 `/billing`、`/billing/folios/:id`、价目维护页；StayDetailView 有客账入口。费用、实收、预收剩余、退款、未付余额分别展示；不能把所有金额合成“收入”。
- 续住更新计划不自动证明已收款；换房后的费用关联正确使用段；退房与结账各有入口，存在欠费时明确提示，不能擅改 V1 退房的原默认规则。

### 11.5 验收

金额精度与边界、部分收款、多笔预收、服务取消/履约唯一、价目改价不改旧账、跨日/换房/续住、退款额度、并发退款、重复点击、关闭后调整策略、历史 V1 接入、撤权、事务失败、受限运行角色，以及上述 430 元例均须覆盖。普通收据不标为法定发票。

## 12. V2.1 收银交班、营业日与经营报表

- 新 `cashier_shifts`、`cash_counts`、`business_days`、`daily_close_runs`、日报快照/调整表，与 V1.3 的事项交班分开。
- 权限 `cashier:operate`（前台/总经理）、`cashier:close` 和 `report:finance`（总经理）；业务角色与财务可见范围明确，不向客房服务员暴露金额。
- 收银班次 `OPEN → SUBMITTED → CONFIRMED`；期初备用金、现金收退款、期末实盘及差异原因独立字段，不能为平账修改旧收款。
- 营业日配置必须明确。关账默认人工核对触发：锁营业日 → 校验未完成批次 → 按唯一来源计入应记房费 → 校对费用/资金 → 固化报表 → 标记 CLOSED，共同使用可恢复/幂等批次。日批单实例通过数据库锁保证，不依赖 JVM 静态锁。
- 不因日切自动退房。原营业日关闭后不改原日报，以当期调整关联原营业日；首版不提供任意“重开已关账日”。
- `POST /api/cashier-shifts`、`/{id}/submit`、`/confirm`；`GET /api/business-days`、`POST /api/business-days/{date}/close`；`GET /api/reports/daily`。
- 页面收银交班、营业日待办、日报。明确房晚/可售房分母、维修停售、收入和现金流的口径；没有可靠历史分母时标“数据不足”，不伪造 ADR/RevPAR。
- 验收日切前后边界、重复/中断关账、部分失败重试、跨班收款、实盘差异、关账后调整和追溯、报表总额与来源明细一致。

## 13. V3.0 预订与未来库存

### 范围和状态

首批一单一房、可多晚，手工登记电话/线下/OTA 来源及外部单号；房型预订与实际房号分配分开。状态 `HELD/CONFIRMED/CANCELLED/NO_SHOW/CHECKED_IN`；保留单有明确到期时间，取消/未到店按配置规则释放库存。预订转入住关联既有 Stay 事实，不把预订单直接改成入住使用段。

### 数据与库存协议

- 新 `reservations`、按房型/日期的库存分配或计数行、房号排房引用、未来停售区间、预订事件；到离店区间采用 `[arrivalDate,departureDate)`。
- 默认禁止超卖；修改日期/房型采用同一事务先锁旧新日期并核验，再释放/占用，失败保留原预订。
- 房型/日期库存锁行必须可靠存在：预生成或 INSERT ON CONFLICT 后有序 FOR UPDATE，不能先 SELECT 空行就认为锁住名额。
- 一个占用只计一次。预订转入住后预订占用转移给实际入住或保留同一分配主体，不能同时减“已预订”和“在住”两次；变更与取消有唯一补偿事实。
- 将续住/缩短、换房、退房与未来库存衔接纳入同一版，按第 5.4 节统一锁序；实际超期未退要提示未来冲突，不自动赶客/释放实际房间。
- 当前 DIRTY 不能简单当作所有未来日期永久停售；维修停用和计划停售有日期区间，实际可入住仍由 RoomEligibility 最终判定。
- 预订订金复用 V2 的真实资金记录及可追溯关联，转入住客账不重复记收款；取消罚金按明确政策形成费用。

### 接口、页面和验收

建议 `/api/reservations`、`/{id}/confirm`、`/cancel`、`/mark-no-show`、`/assign-room`、`/check-in`；`/api/availability?arrivalDate=...&departureDate=...`、`/api/inventory/blocks`。新权限 `reservation:manage`（前台/总经理）、`inventory:manage`（总经理）。

前端 `/reservations`、`/reservations/:id`、`/availability`；先做清晰日期网格和普通编辑，不引入复杂拖拽日历依赖。若加拖拽，仍调用同一校验接口，失败恢复原位置。

验收最后一间并发预订仅一笔成功、跨夜区间、取消释放、到期释放幂等、修改失败不丢旧库存、转入住不双扣、提前退房/续住冲突、实际房间清洁阻止、停用区间、外部单号重复及订金迁移不重复计收。

## 14. V4.0 首个渠道连接

### 先做供应商无关核心

- `integration` 内定义小型供应商 adapter，不把厂商字段渗入 Stay/Reservation 核心 DTO。
- 表建议 `channel_connections`、`channel_mappings`、`inbound_events`、`outbox_events`、`sync_attempts`、`reconciliation_runs`。凭据保持 Git 外配置或独立安全引用，普通查询不返回。
- `inbound_events` 以供应商/外部事件唯一，认证签名并验证防重放；重复、乱序、过期事件按供应商版本/序号协议处理，不能统一用到达时间覆盖。
- 入站持久化后通过同一预订服务处理；出站业务变更与 outbox 在一个本地事务，后台工作器以数据库有序领取/有界重试执行。外部 HTTP 不放在持有房间/库存事务锁的长事务内。
- 展示最后同步时间、错误、重试次数、人工处理状态；失败退避有上限，需人工处理时保留事实，不无限重试。

### 连接完成的门槛

首个供应商必须有用户指定、合法接口权限、正式文档、沙箱/测试账号、房型/价格映射与回调认证方式。不能猜测携程等私有接口，不能绕过权限抓取后台。缺少条件时可完成 adapter 协议、持久化和可控模拟测试，但该渠道状态保持 `BLOCKED_EXTERNAL`，不宣称端到端集成通过。

新 `channel:manage` 默认总经理；账号/凭据系统操作再按授权限制。接口 `/api/channels`、映射维护、同步任务查询/重试；供应商回调如需免 CSRF，只对精确回调路径应用并由签名认证保护，不能关闭全局 CSRF。

验收供应商沙箱中的接单/变更/取消/库存与价格同步、重复乱序回调、超时后查询、签名失败、断网重试、对账差异、停售/人工接管，以及连接故障不破坏店内入住清洁。iCal 不替代实时订单/价格/付款同步。

## 15. V4.x 直订和线上支付（独立条件小版）

- V4.1 可做官网或小程序直订，复用 V3 库存服务；公开端与员工端路由/权限分开，公开 DTO 不能泄露员工接口或住客资料。限流、预订保留到期、取消和防刷作为闭环一起验收。
- V4.2 可做正规支付适配：`payment_intents`、`provider_transactions`、回调事件、对账、退款任务；外部交易与 V2 的记账事实分开，通过唯一外部交易映射记账。
- 托管收银台/令牌化由支付机构处理；不保存卡号敏感认证数据。金额、币种、订单、签名与通知来源服务端核验，不信浏览器“支付成功”。
- 请求超时先查交易，不盲目重扣；退款有额度、权限、异步状态、失败恢复和对账，不能收到回调前就写成实际退款成功。
- 每个小版都需要明确供应商和测试环境。无凭据只完成内部框架与模拟，不冒充真实支付联调。线上支付如有明确优先需求，可在 V2 稳定后独立提前安排，并在进度表记录用户调整顺序。

## 16. V5.0 客户与精细运营

只选择已经有实际经营价值的一条闭环，默认不把会员、协议客户、营销和物料库存一起打包。

## 17. V6.0 多门店（条件版本）

实际有第二店或明确 SaaS 目标才启动，单店期间不预先全库加 tenant_id 或拆微服务。

- 先建立门店边界、门店成员与岗位、跨店总部权限、门店时区/币种/营业政策，再按模块逐步迁移数据。
- 房间、库存、预订、入住、任务、客账、收银和业务审计都归属门店；关联外键/唯一键防止跨店串联，不能仅在前端传 storeId 过滤。
- 单店旧数据迁入一个显式默认店，迁移前后校对数量和金额；管理员的技术身份不自动跨店访问客资或资金。
- 门店内唯一编码与全局 ID 分清；幂等范围、外部渠道连接与权限都校验门店上下文。跨店客历/资金/库存共享需另定规则，不默认互通。
- 验收每个接口的跨店 ID 探测、旧数据迁移、门店角色撤销、总部汇总口径、跨店同码、备份与恢复。业务服务仍可保持一个模块化单体。

## 18. 多智能体分工与共享文件协议

本文允许后续在用户授权的任务范围内使用多智能体协作，但不要求每个小任务都启动多个智能体。多个智能体不是同时各做一个不同产品版本；当前必需版本验收前，不启动下一个产品版本的实现。

### 18.1 建议角色与交付物

| 角色 | 文件所有权与职责 | 交付要求 |
| --- | --- | --- |
| 协调/集成智能体 | 本文进度/决策、API/DATABASE 合约、迁移号、公共入口、最终验收 | 负责唯一集成顺序与完成判断 |
| 后端智能体 | 分配的领域 Service/Mapper/DTO、领域测试 | 按冻结合约交付，不擅改共享角色/错误/幂等基础设施 |
| 前端智能体 | 分配的 views/components/types/领域样式和浏览器场景 | 复用风格，合约驱动；不得只交静态演示 |
| 测试/复核智能体 | 只读复核、指定测试文件、证据分析 | 查权限/并发/故障及手机体验，不能并行占用同一测试数据库 |

协调者可兼任任何角色，小版本不必凑齐四人。派发任务时明确当前版本、输入合约、允许修改文件、不得修改文件、依赖、验收命令和交付格式。

### 18.2 共享文件只由一个写入者维护

这些默认由协调者串行维护：`pom.xml`、`package*.json`、`main.ts`、公共 CSS、router/index、WorkspaceLayout、RolePermissions、ApiErrors、IdempotencyService/StayMapper 共享部分、迁移目录编号、runtime-grants、PRD/DATABASE/API、本文进度。

领域智能体需要共享改动时提交准确建议/补丁给协调者；不要与另一个智能体同时编辑同一文件。工作树隔离可用 `codex/` 分支或 worktree，但不能假定不同目录就隔离了 Docker、数据库和固定端口。只有协调者运行独占完整回归。

### 18.3 每个子任务的交接格式

```text
版本/任务ID：
已完成：真实可用行为及对应文件
公共文件改动建议：
合约或迁移变更：
已执行验证：命令、退出码、报告绝对路径
未完成/已知失败：准确复现与影响
下一步：具体文件/接口/场景
运行中进程或会话：PID/命令/端口/日志，或“无”
```

协调者必须读交付内容和实际 diff，不能只依靠智能体自述“通过”。发生合约冲突先统一再集成；保护用户原有修改，不用 reset/清理来消除冲突。

### 19.3 必须覆盖的风险

新增业务按本版场景测试，同时回归五角色/多角色、撤权禁用竞态、幂等重复/异 payload、版本冲突、并发资源竞争、数据库约束、写失败/审计失败完整回滚、网络结果不确定、受限运行角色、原业务兼容。

完整浏览器验收保持 `workers:1`、`retries:0`、trace off 与现有敏感错误快照控制，不以重试掩盖 flaky。不随意延长断言/启动超时或跳过失败。短生命周期独立 Java 验收子进程保留现有启动优先参数与 20 秒数据库 ready 探测；不能把该测试参数抄入生产当作已验证的调优。

计时类 Playwright 测试必须在页面创建定时器前安装模拟时钟，先等待初始真实请求完成再开始统计；不用任意 sleep 代替条件等待。390px 与桌面视口检查页面溢出、操作可达、空/错/加载状态；金额/敏感数据/状态文字必须可读。

### 19.4 同批证据与产物

每次验收新建 `.local/releases/<version>/<timestamp>-<run-id>/`，不得覆盖旧失败。开跑前归档旧 Surefire/浏览器报告，保存 Git HEAD + 实际源码 SHA256、命令/时间/工具版本、开发/测试容器 ID/StartedAt/Paused、必要配置的脱敏标识。

交付记录 `docs/releases/Vx.y-DELIVERY.md` 包含：候选基线、已做/未做、迁移与兼容、命令与统计、证据位置、界面核对、限制与下一步。只记录脱敏信息，不提交原始日志/数据库备份或凭据。

### 19.5 中断后怎么继续

1. 先读第 20/21 节和当前版交付记录，查看 Git diff、报告时间和进程状态。
2. 若原测试仍运行，继续观察原进程/日志，不重复启动；若已退出，检查真实退出结果。
3. 无最终结果的旧批次标 `INTERRUPTED`，原样留存；不得拼接前后通过部分凑整版。
4. 只恢复未完成步骤。源码未变且已有有效同批完整报告时，不因换智能体无故重跑全部；缺证据或源码变动则明确重新验证范围。
5. 恢复进度与原因写回第 21 节，继续当前授权的下一步。
