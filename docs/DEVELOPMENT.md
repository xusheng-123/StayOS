## 1. 项目技术方案（建议）

| 部分 | 建议技术 | 初学者理解 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 员工在浏览器中看到并操作的页面 |
| UI 组件 | Element Plus | 提供表格、表单、弹窗等常见界面组件 |
| 后端 | Java + Spring Boot | 处理业务规则、校验请求、访问数据库 |
| 权限 | Spring Security | 检查是谁登录、是否允许执行某项操作 |
| 数据访问 | MyBatis-Plus | 帮助 Java 程序读写数据库，复杂查询可编写明确 SQL |
| 数据库 | PostgreSQL | 长期保存员工、房间、入住和任务数据 |
| 数据库变更 | Flyway | 按版本记录数据库表结构如何变化 |
| 页面数据更新 | 操作后刷新、房态定时查询及手动刷新 | 第一版不要求 WebSocket，提交时后端再次检查 |
| 版本管理 | Git | 保存代码变化记录，便于回看和回退 |
| 运行环境 | Docker + Linux，部署阶段再完善 | 让系统在相对一致的环境中运行 |
| 自动化测试 | JUnit；需要时使用 Testcontainers | 自动重复检查核心功能有没有出错 |

Java、Spring Boot、PostgreSQL、MyBatis-Plus、Spring Security、Flyway、Vue 3、TypeScript、Element Plus 和 Git 已确定，不再在多个替代技术中摇摆。Vite、Docker 和具体测试工具按阶段落实。工程启动时核对官方支持情况并记录实际版本；本次不提前锁死版本。

## 2. 什么是前端、后端、数据库和接口？

- **前端**：员工使用的网页。负责显示房间、表单、按钮和操作结果。
- **后端**：运行在服务器上的程序。负责判断操作是否合法、执行业务规则、写入数据库。
- **数据库**：长期保存业务信息的系统。关掉浏览器后，已保存的入住记录仍应存在。
- **接口/API**：前端向后端提交查询或业务操作的约定方式。
- **部署**：把程序放到一台服务器上，使其他设备可以访问。
- **Git**：记录代码版本的工具。提交一次变更后，可以查看修改内容或回到之前的版本。
- **测试**：用事先准备的例子检查软件是否按预期工作。

## 3. 建议的整体架构

第一版采用“模块化单体”架构：后端作为一个应用运行，但内部按业务职责划分模块。不建议一开始就拆分成微服务。

```text
员工浏览器
  ├── 前台页面
  └── 客房部页面
        │
        ▼
     前端应用（Vue）
        │ 通过接口发送请求
        ▼
     后端应用（Spring Boot）
        ├── 登录与权限
        ├── 房间管理
        ├── 入住/退房/换房
        ├── 客房清洁
        ├── 异常处理
        └── 操作记录
        │
        ▼
     PostgreSQL 数据库
```

【注释】“模块化单体”不是把所有代码写在同一个文件里，而是一个后端应用中仍然有清晰的业务模块。这样第一版简单一些，未来也能继续扩展。

## 5. 后端代码如何分工（概念示例）

可按业务领域组织代码，例如：

```text
backend/.../room/             # 房间查询和管理
backend/.../stay/             # 入住、退房、换房和房间使用历史
backend/.../housekeeping/      # 清洁任务和清洁状态
backend/.../auth/              # 登录与权限
backend/.../staff/             # 员工账号与固定角色分配
backend/.../guest/             # 最少必要的住客资料
backend/.../issue/             # 房间异常及解除阻止
backend/.../audit/             # 审计记录
```

一个后端业务通常会经历几个环节：

1. **Controller（接口入口）**：接收网页传来的请求。
2. **Service（业务处理）**：执行规则，例如检查房间是否可入住。
3. **Mapper/Repository（数据访问）**：读写数据库。
4. **Entity/DTO（数据结构）**：表达数据库对象或接口收发的数据。

【注释】这是常见分层思路，不要求初学者一次性理解所有细节。可以把它想成“接待窗口—业务办理人员—档案室”：接口入口接收请求，业务层作判断，数据访问层与数据库交互。不要让页面直接绕开后端修改数据库。

第一版后端保持一个 Maven 工程，按模块内的 `controller/service/mapper/entity/dto` 分层，不预先拆成多个独立服务，也不要求每个简单类都配接口和实现类。跨模块由业务层调用，例如退房调用清洁模块建任务，两者参加同一数据库事务。

| 问题 | 当前决定 | 对应文档 |

| 异常处理 | `OPEN → RESOLVED`，员工可上报，主管/总经理解除阻止，互不覆盖清洁状态 | PRD 第 4.5 节；API 第 10 节 |
| 异常类型 | 影响入住的设备故障、严重卫生问题强制阻止；遗留物品及其他问题默认不阻止，可选择阻止；无规则配置页 | PRD 第 4.5 节；API 第 10 节 |
| 任务分配 | 仅主管/总经理单间或批量分房，所有角色关闭自主领取；执行人只能完成自己的任务 | PRD 第 2.6、4.3 节；API 第 9 节 |
| 基础管理 | 五个固定角色、一人可多角色；账号管理及房型/房间维护默认仅管理员 | PRD 第 2.6 节；API 第 5、11 节 |
| 操作时间 | 实际操作用服务器时间、`TIMESTAMPTZ`，预计退房由前台填写，无历史补录 | API 第 2 节 |
| 早期验收依赖 | 阶段 3、4 使用虚构夹具验证状态和入住，阶段 5、6 再通过正常页面流程复验 | 本文阶段 3—6；API 第 15 节 |

四项复核方案（受控接管、故障换房关联异常、固定异常类型与阻止规则、早期测试夹具和后续页面复验）已经用户接受，按上表执行，不重复询问。首个管理员及登录方式已落实；第 2 阶段确认的房间规则见 ROOMS.md。第 3 阶段确认全部实际住客及加密脱敏、PostgreSQL 入住幂等及 24 小时策略，见 CHECK-IN.md。真实试用的个人信息保留、身份核验、部署及外设仍按 PRD 第 9 节等待确认。

**遇到未决事项的协作规则：** 现在不集中要求用户回答。制作过程中一旦当前任务需要这些决定，先说明具体问题、影响和选项，立即暂停当前开发任务，等待用户明确反馈后再继续；不得一边等待一边实现相关假设，不得把初始建议或用户沉默视为授权。按钮样式等普通细节可采用合理默认值并记录，已确认规则不反复问。

## 6. 开发顺序建议

### 阶段 0：统一设计文档
- 同步根目录 README 和 docs 中四份文档的第一版范围，收费内容明确移至第二阶段。
- 固定清洁不验收、任务分配、异常处理权限、房态判断和房间使用历史模型。
- 补齐账号、角色分配、房型维护、任务分配和历史查询接口，移除客户端指定实际退房时间的示例。
- 区分已确定规则与初始建议，保持表名、状态、字段、角色和验收场景一致。
- 纳入受控接管、故障换房异常关联、固定类型阻止规则及阶段测试依赖，补充相应验收场景；登记遇到未决事项即暂停等待用户反馈的规则。

完成标志：五份文档对同一业务能给出一致结果；第二阶段收费不再成为第一版前置条件。仅更新文档，不执行建表、不生成工程。

### 阶段 1：建立开发环境
- 安装当前受支持版本的 JDK、Node.js、Git 和 PostgreSQL，或在后续选择 Docker 管理开发服务。
- 建立 Git 仓库。
- 创建 Vue 与 Spring Boot 基础工程。
- 建立本地开发配置，确保密码等机密不提交到仓库。
- 接入 Flyway，确认空数据库能迁移、重复启动不会重复建表；建立统一错误响应，前端成功调用后端。

完成标志：按 README 可在新环境启动前后端并连接 PostgreSQL，空库迁移成功，基础接口调用正常。当前已初始化 Git；实际启动和测试命令以根 README 为准。

### 阶段 2：登录与权限
- 实现登录、退出和当前用户查询。
- 建立系统管理员、前台、客房服务员、客房主管、酒店总经理角色。
- 实现账号新增、查询、禁用、重置密码和给员工分配固定角色，支持一人多角色。
- 酒店总经理拥有前台和客房业务权限；账号、角色分配和房型/房间维护默认仅管理员，管理员不自动拥有业务办理权限。
- 建立成功、失败及拒绝操作的审计基础能力；成功记录参与业务事务，失败/拒绝记录独立保存。
- 在后端为接口实施权限检查。

完成标志：五个角色访问受限接口正确允许或拒绝；总经理不能管理员工或给自己提权；禁用、重置密码或角色调整后旧会话及时失效或重新校验，不能只靠前端隐藏按钮。

### 阶段 3：房型与房间
- 实现房型、房间新增、查询、修改及受控停用，不删除关联历史。
- 添加测试房间数据，如 801、802、803。
- 为早期验收准备仅限开发/测试环境的虚构测试夹具（即预先准备的数据），包含清洁合格、待清洁、占用及存在阻止异常的房间，不依赖尚未完成的清洁/异常页面。测试数据按所处阶段需要准备表结构，不绕过生产规则或引入生产数据修正接口。
- 实现按楼层、房型、房态筛选。
- 实现统一可入住判断与分维度房态返回，新房默认待清洁，不提供直接任意改综合房态的接口。

完成标志：重复房号被拒绝，停用房不能分配；占用、异常、清洁分别影响可入住性，刷新后数据一致。存在当前占用或未完成任务时不能停用房间档案。此阶段通过夹具验证查询/判断规则，尚不宣称完整业务闭环。房号规则已于 2026-10-20 确认：无历史可改，有历史禁止直接改号。当前用户命名的“第 2 阶段”对应本节，实际规则和接口详见 ROOMS.md。

### 阶段 4：办理入住
- 登记必要住客及预计退房时间，创建入住和第一段房间使用记录。
- 在后端重新检查可入住条件，使用数据库约束与锁保护当前占用。
- 落实关键写操作防重；入住已确认 PostgreSQL 及 24 小时防重方案，详见 CHECK-IN.md；其他业务开发时核对。不用按钮防重复代替后端保证。
- 沿用阶段 3 的虚构测试夹具验证入住，阶段 5、6 再用真实清洁/异常页面复验，不能为演示开放直接改房态。

完成标志：正常入住成功，脏房、故障房、停用房和占用房均被拒绝；两人同时抢同一间房只一人成功；同一请求重试不重复创建入住；预计退房时间到达不释放房间。

### 阶段 5：退房与清洁闭环
- 退房同时结束入住和当前使用段，原房标脏，创建关联来源段的清洁任务。
- 实现任务列表、详情、分配、改派待处理任务、分配后由负责人开始、完成自己的任务及任务历史。
- 实现执行人无法继续时主管/总经理的受控接管：必填原因、新执行人合法性、预期原执行人校验、原开始时间与交接历史保留，不改变清洁中状态，不直接完成。
- 支持主管/总经理为无人入住且无未完成任务的房间人工创建清洁任务。
- 保存任务、清洁状态及任务日志，整个动作保持事务一致；不增加主管审批。

完成标志：退房任务仅一条，任务创建失败时退房整体回滚；并发分房仅一方成功，自主领取被拒绝，服务员不能操作他人任务；执行人被禁用、失去权限或无法继续后可受控接管，旧执行人不能再完成，非法接管被拒绝；接管与完成并发不覆盖结果。通过正常页面创建/完成清洁任务准备可入住房间，再复验阶段 4 入住条件，旧任务重复完成不覆盖新状态。

### 阶段 6：换房与异常闭环
- 换房关闭原使用段、创建新段、写换房记录，原房标脏并创建来源为换房的任务，同事务完成。
- 提交原段 ID 防止旧页面重放，退房与换房互斥，多房间按固定顺序锁定。
- 实现异常上报、查询、主管/总经理确认解决，异常阻止与清洁、占用分开。
- 实现固定异常类型白名单及强制/可选阻止规则，不增加规则配置页。故障换房先创建或关联原房未解决的阻止异常，换房失败保留此前已上报异常。

完成标志：连续换房历史完整；目标房冲突或中途失败时无部分更新；故障换房关联缺失、关联他房、已解决或非阻止异常时均被拒绝；强制类型传 false、未知类型被拒绝。通过正常页面上报/解决异常、处理清洁，再复验阶段 3、4 的完整入住条件；清洁不解除故障、解除一个故障不忽略其他故障、解除故障不自动清洁合格；已入住异常不自动退房。

### 阶段 7：业务页面与历史完善
- 完善前台、客房部工作台及总经理的业务入口，复用已有业务页面。
- 完善入住、换房、任务、异常历史及按范围查询关键操作记录。
- 统一失败提示、表单校验、操作成功后的刷新，房态页支持定时查询和手动刷新。

完成标志：各岗位可通过界面完成完整业务；直接调用接口仍受权限约束，服务员不能查看不必要住客资料；关键操作可追溯人、时间、对象及结果。

### 阶段 8：完整测试与试运行
- 测试正常流程、错误输入、权限边界、重复请求、并发操作。
- 配置日志和数据库备份。
- 练习恢复备份。
- 先在测试环境试运行，再评估正式部署。
- 用真实 PostgreSQL 测试核心约束、锁和事务，不只依赖内存数据库或人工点击。
- 演练从空环境安装、Flyway 升级和备份恢复，完善启动、操作及故障处理说明。

完成标志：PRD 验收清单通过；没有重复占房、重复任务、越权或事务半完成；恢复后业务历史完整；测试环境可按文档重新部署。

### 第二阶段：额外服务与收费（不属于第一版工程阶段 0—8）

第一版完成后再确认服务目录、服务订单、房费规则、账单明细、收款、押金、优惠与退款范围，以及退房与结算的关系。按确认范围新增迁移、接口和页面，不提前创建空表或空接口。

扩展时服务订单关联入住及发生时的房间使用记录，名称、单位和价格保留快照；应收与实际收款分开，历史金额调整可追溯。不按最新房型价格倒算第一版未记录的历史费用。

第二阶段验收方案在规则确认后另行制定，不成为第一版交付条件。

### 6.1 每阶段共同的可靠性要求

入住、退房、换房、清洁和异常功能都随开发补充成功审计、错误处理及必要测试，不等最后阶段再做。事务保证一起成功或失败，并发控制保证多人同时操作仍正确，幂等保证同一次请求重试不重复产生业务；三者不能互相代替。

数据库锁定顺序、部分唯一索引和跨表一致性规则以 DATABASE 第 6 节为准。先使用 PostgreSQL 事务、行锁和约束，不为第一版引入分布式锁、消息队列或微服务。

## 7. 如何与 AI 编程工具合作

AI 可以协助生成代码，但不应一次性让它“生成整个系统”。推荐一次只交付一个小任务，并要求它说明改动、运行测试、列出未完成事项。

每次任务可按下面的模板描述：

```text
请先阅读 docs/PRD.md、docs/DATABASE.md、docs/API.md 和 docs/DEVELOPMENT.md。

本次只完成：<写清一个小功能>。

要求：
1. 不要擅自改变已经确认的业务规则。
2. 已确定规则按文档执行；发现新矛盾或影响核心流程的信息缺失时说明影响。普通细节采用合理默认值并记录，只有影响当前任务的关键决定才需要澄清。
   对 PRD 第 9 节登记的未决事项及新出现的关键选择，遇到时立即暂停当前开发任务，提出具体问题并等待用户明确反馈后再继续；不得自行采纳初始建议或默认沉默同意。已确认规则不重复询问。
3. 后端必须校验输入、权限和业务状态，不能只在前端限制。
4. 为本次功能补充必要的自动化测试。
5. 完成后说明改动了哪些文件、如何运行、测试结果是什么、还有哪些已知问题。
6. 不要把真实密码、密钥或真实客人个人信息写入代码、示例或日志。
```

【注释】这里的“请先阅读文档”能减少 AI 在不同阶段重复创造规则。若业务确实需要变更，先更新相关文档，再让 AI 修改代码。

## 9. Git 的最简使用习惯

建议经常保存小而完整的代码版本，例如：
- `初始化前后端工程`
- `完成房间列表查询`
- `完成入住接口与测试`
- `完成退房创建清洁任务`

每次提交前，先检查修改了什么，并确保没有密码、密钥、真实客人数据、构建产物或不需要的临时文件。

## 10. 正式上线前的最低准备

1. 开发、测试、生产环境分开。
2. 使用 HTTPS 并限制访问权限。
3. 使用强密码、安全保存凭据，不将机密写进 Git。
4. 设定数据库备份周期和独立备份存储位置。
5. 定期从备份恢复，验证真正可恢复。
6. 记录关键操作和系统错误，同时避免泄露敏感信息。
7. 制定系统不可用时的人工登记和恢复后核对流程。
8. 测试数据库升级步骤，确保升级失败时有恢复方案。
9. 在真实酒店试用前，获得酒店流程负责人确认，并用虚构数据进行充分测试。

## 11. 本项目目前不需要急着做的事

- 不要一开始拆成微服务。
- 不要为了“以后可能用到”同时引入很多中间件。
- 不要先做复杂仪表盘而忽略入住与退房的一致性。
- 不要把 WebSocket 当作保存业务数据的地方。
- 不要只靠手工点击测试。
- 不要在第一版开发服务目录、订单、计费、账单、押金或收退款，也不要要求退房先完成结算。
- 不要为以后可能用到的收费功能提前创建空表、空接口和页面入口。
- 不要只改入住记录中的房号而丢失使用历史，也不要让清洁任务只有房号没有来源。
- 不要让清洁完成直接解除故障，或让故障解决直接变成清洁合格。
- 不要直接用真实客人数据测试。
- 不要未经测试就把开发版用于真实营业。

## 12. 推荐阅读顺序

1. `PRD.md`：先了解系统到底要做什么。
2. `DATABASE.md`：了解系统要保存哪些数据。
3. `API.md`：了解网页与服务器如何交换数据。
