# 第 5 阶段：客房清洁任务管理

本文件描述实际接口和业务规则。第 4 阶段的退房任务保留并扩展，不增加收费、住中清洁、主管验收、换房或维修工单。交付与实际测试结果见根目录 [PHASE5-DELIVERY.md](../PHASE5-DELIVERY.md)。

## 业务规则

- 三个任务状态：`PENDING → IN_PROGRESS → COMPLETED`。分配和重新分配只改变归属，不提前开始清洁。
- 人工任务：空闲、`DIRTY`、无未完成任务的真实房间；主管或总经理提供创建原因。`MANUAL / MANUAL_CLEANING`，入住和使用段关联必须为空。每次新建单间任务，不批量修改现有 80 间房。
- 退房任务：`CHECKOUT / CHECKOUT_CLEANING`，仍保留原房间、入住及使用段的复合外键、来源唯一性；初始未分配、`PENDING`，与退房同事务创建日志。
- 自主领取已关闭：包括普通服务员、主管和总经理在内的所有角色均不得调用 claim；服务员仅查看和执行已分配给自己的任务。历史 CLAIM 日志及 claimed_at 保留，不再生成新的领取事件。
- 分配：主管/总经理为未分配 `PENDING` 任务选择启用且有 `housekeeping:execute` 权限的账号。主管和总经理也可执行，但必须先成为负责人。
- 重新分配：仅主管/总经理，为已分配的待处理任务或无法继续执行的清洁中任务指定另一位合格员工，原因必填。清洁中的重新分配就是受控接管，保留最初的 `started_at/started_by`，不重置开始事实，原员工立即失去后续操作权限。`version` 同时核对页面看到的状态和负责人是否仍有效。
- 开始：当前负责人、`PENDING`、房间无人占用且 `DIRTY`，服务器记录开始时间并设 `CLEANING`。
- 完成：当前负责人、`IN_PROGRESS`、房间无人占用且 `CLEANING`，服务器记录完成时间和完成员工，设 `COMPLETED`、房间 `CLEAN`。允许清洁备注，不收集不必要住客资料。
- 维修/启用与清洁独立。允许对停用或存在维修阻止的空闲待打扫房间进行清洁，完成不恢复启用、解除异常或改变占用。最终能否入住仍由统一后端房态规则判断。
- `INSPECTION` 仅保留查询展示，正常清洁不进入该状态。不存在验收、返工、质量评分接口。

## 权限及数据范围

| 角色 | 查询范围 | 执行 | 管理 |
|---|---|---|---|
| HOUSEKEEPING_STAFF | 仅当前分配给自己的任务，包括自己的已完成历史 | 开始和完成自己的任务 | 无 |
| HOUSEKEEPING_MANAGER | 全部任务与历史 | 必须先成为负责人 | 人工创建、分配、带原因重新分配/接管 |
| HOTEL_MANAGER | 同主管，另保留前台入住/退房权限 | 同主管 | 同主管，不自动获得系统管理员权限 |
| FRONT_DESK | 房态查询，不默认开放任务内部详情 | 无 | 无 |
| ADMIN | 保留系统管理；不默认开放清洁任务 | 无 | 无 |

多角色账号按现有权限并集。服务员改变 `scope`、负责人筛选参数、详情 ID 或历史 ID，都不能扩大范围；不属于范围的详情/历史返回 404。主管的负责人筛选选项包含已经禁用/失去执行资格的历史负责人，便于找到并接管任务；实际分配候选仅启用、有执行权限的员工，写入时再校验资格。两类选项均只返回员工 ID 和显示姓名，不开放账号管理接口。

## 已实现接口

所有接口位于 `/api/housekeeping-tasks`，沿用 Session、CSRF、统一 JSON 错误。写操作必须提供 UUID `Idempotency-Key`；不接受客户端指定实际操作时间、任意状态或操作者。

| 方法 | 路径 | 功能与权限 |
|---|---|---|
| GET | `/api/housekeeping-tasks` | 有范围限制的列表，`housekeeping:read` |
| GET | `/{id}` | 任务详情，校验范围 |
| GET | `/{id}/history` | 追加的操作历史，范围同详情 |
| GET | `/statistics` | 当前授权范围统计 |
| GET | `/employees` | 合格分配候选，`housekeeping:manage` |
| GET | `/assignees` | 查询筛选用负责人，包含已有任务的历史负责人，`housekeeping:manage` |
| POST | `/manual` | 人工创建，`housekeeping:manage` |
| POST | `/{id}/claim` | 已关闭，所有登录角色均返回 403；未登录 401 |
| POST | `/{id}/assign` | 首次分配，`housekeeping:manage` |
| POST | `/{id}/reassign` | 待处理改派或清洁中受控接管，`housekeeping:manage` |
| POST | `/{id}/start` | 当前负责人开始 |
| POST | `/{id}/complete` | 当前负责人完成 |

表中简写路径均以 `/api/housekeeping-tasks` 为前缀。原规划中的 `/logs`、`/takeover`、`/api/housekeeping-assignees` 和“领取并开始”合并动作未提供，统一采用上表明确动作。

人工创建请求：

```json
{ "roomId": 1, "reason": "初始客房清洁" }
```

开始：`{ "version": 0 }`（使用实时版本）；完成可带 `reason` 作为清洁备注。首次分配与重新分配：

```json
{ "version": 2, "assigneeId": 5, "reason": "原员工临时离岗，由其他员工继续清洁" }
```

`version` 为详情中的当前版本，非负整数，每次成功操作递增。`assigneeId` 只允许在分配/重新分配动作中出现；重新分配和人工创建的原因必填，其余备注选填，最多 1000 字。

写入成功返回历史回执：`id`（日志 ID）、`taskId`、`action`、`fromStatus/toStatus`、`fromAssignee/toAssignee`、`operatorId`、`operatedAt`、`taskVersion`、`reason` 及相关显示姓名。回执描述操作发生时的事实，当前状态以重新查询的详情为准。任务详情包含负责人、分配/领取/开始/完成时间、最初开始员工、最终完成员工、创建和完成备注；不关联或返回住客完整身份信息。

列表参数：

- `page` 默认 1（1—100000），`pageSize` 默认 20（1—100）。
- `roomNumber` 最长 20，去两端空白、转大写，字面包含搜索；`floor` 为 -99—199 且不为 0。
- `status` 可省略或 `PENDING/IN_PROGRESS/COMPLETED`。
- `scope=ALL/MINE/UNASSIGNED`，默认 ALL，始终叠加服务器的数据范围限制。
- `assigneeId` 负责人，普通服务员只能指定自己，否则 403。
- `sort=NEWEST/OLDEST`，默认最新创建在前，使用 ID 作为相同时间的稳定排序条件。

统计为当前用户授权范围的待处理数、清洁中数、今日完成数、自己负责的未完成任务数、未分配数；今日按 `Asia/Shanghai` 的自然日计算。统计不随当前房号/楼层筛选变化，列表计数随筛选变化。

主要错误：400 输入或标识不合法；401 登录失效；403 无动作权限/非负责人；404 不存在或无记录查看权限；409 `TASK_CONFLICT`、`TASK_ALREADY_EXISTS`、`IDEMPOTENCY_MISMATCH`、`IDEMPOTENCY_KEY_EXPIRED`。错误仅返回中文业务提示，不返回数据库异常堆栈。

## 事务、锁和防重复

同一事务完成任务变化、房间清洁状态变化、历史、成功审计和幂等结果。失败全部回滚，允许修复故障后用原标识重试。

沿用同一幂等表及原有 HMAC 内容摘要：新增 `HK_MANUAL_CREATE/CLAIM/ASSIGN/REASSIGN/START/COMPLETE` 操作类型和 `result_task_log_id`，不改变入住/退房的操作类型、24 小时行为或结果关联。同一操作人＋操作类型＋请求标识，相同内容在 24 小时内返回原历史回执；内容不同拒绝，超时旧标识保留且拒绝，不保存整份请求或响应。

锁定顺序：请求预留 → 涉及员工按 ID 升序共享锁 → 房间 → 任务 → 日志/审计/结果。共享员工锁避免校验资格后被并发禁用/改角色；账号管理不反向锁房间/任务。入住仍按原房间锁，退房仍按入住 → 房间 → 使用段，清洁不反向锁入住记录，因此兼容既有顺序。任务先读取房间 ID，但真正加锁和重检始终先房间后任务。

房间部分唯一索引覆盖 `PENDING` 和 `IN_PROGRESS`。分配竞争、完成与接管竞争还必须在行锁后核对版本、状态和归属，数据库唯一约束不能代替业务验证。历史以任务版本唯一，只开放查询和业务内追加，不提供修改/删除历史接口。

## 页面与操作

本地地址：[清洁任务工作台](http://127.0.0.1:5173/housekeeping/tasks)。主管优先进入“人员分房”，选择员工、多选房间并一次确认，无任务的合法待打扫房间自动建单；单间人工建单及分配仍保留。分配后，负责人“开始打扫”，随后“完成清洁”。主管选择“重新分配”并填写原因处理接管。手机使用卡片，操作按钮至少 44px 高。

详情抽屉展示当前信息、执行时间及操作历史。任务页操作后自动重新查询；前台通过“刷新房态”或重新进入页面获取最新状态，未实现 WebSocket 推送。

提交中禁用重复按钮。响应丢失或内容损坏时复用原标识与内存中的原请求重试；也可先关闭操作弹窗、核对任务结果。浏览器仅保存请求标识、动作、任务/房间 ID，不保存清洁备注或完整请求。刷新后原请求内容不恢复，不自动重发；先查询详情/历史，明确点击“核对后结束重试”再继续新操作。该动作只清本机提示，不撤销已成功业务。

## 迁移说明

新增 `V9__housekeeping_workflow.sql`，V1—V8 不修改。扩展原任务表的条件来源约束、负责人/执行时间/版本；新增历史表并用既有任务的真实创建时间、创建人补记 AUTO_CREATE。原退房来源唯一、来源使用段唯一和三列复合外键保留。人工任务三项来源关联均为空。未完成房间唯一索引及房态视图同时扩展两种未完成状态。

没有任务取消、独立批量建单、住中清洁、主管验收、维修修复、历史删除或任意房态修改接口。异常模块尚未实现，维修保留行为在隔离测试库通过测试专用阻止事实验证；不将它描述为完整维修业务。

## 第五阶段批量分房优化（当前规则）

仅 HOUSEKEEPING_MANAGER 和 HOTEL_MANAGER 具有 housekeeping:manage。ADMIN、FRONT_DESK、HOUSEKEEPING_STAFF 不得单间/批量分配或改派。ADMIN 没有新增清洁或前台业务权限；原角色权限并集规则保持。所有角色 claim 关闭，服务员列表/统计/详情/历史只包含当前归属自己的任务。

页面 `/housekeeping/assignment`：真实员工卡片（启用且有执行资格）→ 当前未完成房间 → 按楼层/房型/房号筛选 → 多选/取消/全选筛选结果/清空 → 核对员工和房号汇总 → 一次确认。每批 1—100 间。全选跨分页，若超过 100 间提示缩小筛选，不悄悄只分配一部分。房间按楼层、房号数字片段自然排序。列表同时标注可分配、本人/他人已分配、清洁中、已清洁、已占用或状态不符。停用/维修提示单独显示，沿用既有允许清洁但不解除入住阻止的规则。

以下接口均以 `/api/housekeeping-tasks` 为前缀，服务端强制 housekeeping:manage：

| 方法 | 路径 | 内容 |
|---|---|---|
| GET | `/assignment-employees` | 合格员工 ID/账号/姓名/启用状态、待开始/清洁中/上海自然日今日完成数量 |
| GET | `/assignment-employees/{id}/tasks` | 当前员工全部未完成任务；服务员不能用此管理接口查询他人，个人列表沿用原任务列表 |
| GET | `/assignment-rooms` | page/pageSize、roomNumber、floor、roomTypeId、assigneeId，返回每房状态和 assignable |
| POST | `/batch-assign` | UUID Idempotency-Key，加 `{assigneeId, roomIds, reason?}` |
| GET | `/assignment-batches/{id}` | 不可变批次回执，含房号快照、任务/分配日志 ID、是否自动人工建单 |
| GET | `/assignment-results/{key}` | 仅查询当前操作人该标识的已成功批次；未查到返回 404，不代表在途请求已取消 |

批量写入沿用请求预留 → 用户按 ID 升序共享锁 → **全部房间 ID 升序行锁** → 房间对应任务 → 历史/审计/结果。未分配 PENDING 使用原任务；合法 DIRTY 空房没有未完成任务时创建 MANUAL，保存真实创建人及默认“人员分房：初始客房清洁”或填写的原因，不伪造入住来源。每房保存独立 MANUAL_CREATE（如新建）及 ASSIGN 历史。已分配或 IN_PROGRESS 拒绝普通批量覆盖，调整仍须走带原因和版本的 reassign。

整个批次同一个 PostgreSQL 事务，任何房间冲突、历史/审计/结果写入失败全部回滚。输入拒绝空列表、重复/空/非正 ID、超过 100 间。摘要先把房间 ID 排序，因此原标识换数组顺序仍能返回同一回执；更换员工/房间集合/备注拒绝。保留原 24 小时重试、过期拒绝及失败可重试规则。

V10 新增批次表及条目表，idempotency_requests 新增 result_assignment_batch_id；原 V1—V9 不改写，旧入住/退房/任务回执保持原结果字段。批次不保存完整请求或住客资料。前端请求期间禁止重复提交；不确定结果保留原标识和内存原请求，可重试。刷新只恢复标识及房间/员工 ID，不恢复备注；使用结果查询确认，不自动发新请求。

实际验证与限制见 [PHASE5-BATCH-ASSIGNMENT-DELIVERY.md](../PHASE5-BATCH-ASSIGNMENT-DELIVERY.md)。
