# 正式换房（第7阶段）

本文件描述 V12 的实际实现；第7阶段用户指令优先于早期草案。仅 FRONT_DESK、HOTEL_MANAGER 具备现有 `stay:manage` 权限；ADMIN、客房主管及服务员不能办理或读取住客换房历史。多角色继续按权限并集合并。没有收费、自动换房、独立维修工单或清洁验收。

## 业务流程

同一次入住不变，保留住客名单、实际入住和预计退房时间。每次合法换房结束原使用段（ROOM_CHANGE），创建目标房的新段，二者使用同一个服务器 UTC 时间（TIMESTAMPTZ，页面按北京时间展示），保存一条 room_changes 事实。原房释放并设 DIRTY，自动创建未分配 PENDING 的 ROOM_CHANGE_CLEANING 任务；目标房由新有效段派生 OCCUPIED，清洁状态保持 CLEAN。

原因类型 GUEST_REQUEST（住客要求）、ROOM_ISSUE（设施或环境问题）、OTHER，说明必填1–1000字，禁止不必要的住客证件或电话。关联异常仅在 ROOM_ISSUE 下选填；若提供则必须是真实原房异常，不要求故障换房先建异常，不从说明文字推断、创建或解决故障。这是最新指令对早期 NORMAL/BLOCKING_ISSUE 强制关联草案的替代。若确有严重异常，应通过现有上报流程保存，换房不会代替异常管理。

原房未解决 CRITICAL、人工维修停用均保留，清洁完成也不解除。住客仍在原入住中继续入住，最终退房必须提交最新使用段，只处理最终实际房间。

## API

均沿用 ApiResponse、Session 和 CSRF，写操作带 UUID Idempotency-Key。查询权限同正式换房，不为客房角色开放住客历史。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | /api/stays/{id}/room-change/available-rooms | 当前有效入住的可换入目标，房号、楼层、房型及分页参数复用 RoomFilter |
| POST | /api/stays/{id}/room-changes | 正式换房 |
| GET | /api/stays/{id}/room-changes | 同一次入住按时间/ID升序的完整换房历史 |
| GET | /api/stays/room-changes/result/{key} | 仅本人已成功请求的原结果，查询不重执行业务，过期成功记录仍可核对 |
| GET | /api/stays/{id} | 原详情新增 roomSegments、roomChanges，原字段及脱敏住客保留 |

请求示例（仅示意内部ID）：

```json
{"segmentId":20001,"targetRoomId":10005,"reasonType":"ROOM_ISSUE","reason":"空调故障，转入新房继续入住","issueId":30001}
```

issueId 可省略。操作人、时间及状态只能由服务器决定。返回 id、stayRecordId、oldRoomId/newRoomId、oldSegmentId/newSegmentId、原新房号及房型快照、reasonType/reason、可选issueId、changedAt、operatedBy/operatorName、taskId，不返回住客身份资料。客房任务原接口展示 ROOM_CHANGE 来源，但不增加住客资料字段。

错误：400 参数/请求标识非法；401未登录；403越权/账号不可用；404入住/房间/本人结果不存在；409旧使用段、入住结束、目标不可入住、冲突任务、异常关联不匹配或幂等冲突。结果404不代表之前一定失败，应先核对当前入住及历史。

## 统一可入住判断

RoomEligibility 与正式入住共用 room_status.can_check_in：房间启用、空闲、CLEAN、无未完成清洁任务、无未解决严重异常及有效人工停用；不按建议人数强制限制，支持跨房型且不计费。目标列表只用于选择，事务持有房间锁后再查询最新派生事实。原房不能是目标，原房若有异常的未完成清洁任务则拒绝。

## 事务、锁及幂等

预留幂等 → 操作人共享锁及当前权限复查 → 入住行锁 → 原/目标房按内部ID升序锁 → 当前有效使用段锁及二次核对 → 业务写入/清洁历史/成功审计/幂等结果。

不锁另一笔入住；与退房入住→房间、清洁/异常用户→房间→任务/异常相容。两笔入住争同目标、同入住换房/退房、目标入住或异常竞争均由房间/入住锁串行并重新验证。严重异常先提交，后取得房间锁的换房不可基于旧页面成功；换房先完成则仍可上报已入住房的异常，不自动结束入住。

先执行幂等检查再验证旧段。操作人＋ROOM_CHANGE＋UUID识别请求，HMAC内容摘要含入住、段、目标及原因/关联异常；trim后说明用于规范化。24小时同标识同内容返回原不可变换房事实（包括后续再次换房/退房后），不同内容拒绝；过期旧标识拒绝执行；失败整笔回滚并可原标识重试。不存整份请求或住客信息、不自动清理旧标识。

以下原子提交：关闭旧段、建立新段、写换房事实、原房标脏、创建唯一清洁任务及创建日志、成功审计、幂等结果。任务失败、审计失败等均不留下部分占用或历史。

## 数据库

仅新增 V12__room_changes.sql，V1–V11 不改。room_changes 通过两组(id,stay,room)复合外键匹配原/新使用段，原段/新段分别唯一，房间不同；同房异常复合外键，插入触发器核对时间衔接、结束原因和房号/房型快照。没有业务历史删除/更新接口；数据库运维权限仍需单独管理。

housekeeping_tasks 新增 room_change_id，ROOM_CHANGE 来源要求 source_id=room_change_id 且入住/原段/原房真实对应换房事实（四字段复合外键）。保留 CHECKOUT 和 MANUAL 原约束、来源唯一、离房段唯一及同房PENDING/IN_PROGRESS唯一。新来源复用原任务执行与分房流程。

共享 idempotency_requests 新增 result_room_change_id，扩展操作白名单及结果种类检查，旧入住、退房、清洁、异常及批量分房协议不变。当前房间仍仅从有效使用段计算，不建立第二套占用表。

## 页面与安全重试

/stays 当前入住列表、/stays/{id} 入住详情提供“办理换房”；已退房不提供可用按钮。详情保留全部使用段与多次换房历史。弹窗显示必要入住信息、目标分页/房号/楼层/房型筛选、原因及原房异常选填；确认后显示原新房、服务器时间、经办人和清洁任务。

同页响应丢失时锁定请求内容，重试原请求或查询原结果。sessionStorage仅保存随机请求key，说明、住客信息及正文不持久化；刷新后不自动重发，提示查询原结果。查询未确认前保留标识，明确核对后才允许结束本机重试。前台可刷新房态获取原房VACANT/DIRTY、目标OCCUPIED；没有新增实时推送。
