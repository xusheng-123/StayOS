## 1. 项目概述

### 1.1 项目名称
StayOS：酒店前台与客房协同管理系统。

【注释】名称已统一为 StayOS。V1.0 重点是前台与客房部之间的信息协同，而不是一次性覆盖酒店所有经营业务。用户最新开发阶段编号优先：第 1 阶段认证已完成，第 2 阶段房间/房态已完成，见 AUTHENTICATION.md、ROOMS.md 及对应交付记录；收费属于之后的业务扩展阶段。

### 1.2 项目背景
酒店前台需要掌握客房是否可入住，客房部需要及时收到退房清洁等任务。如果主要依靠电话、纸张或即时通信传递信息，可能出现房态更新不及时、任务遗漏、重复安排房间等问题。

### 1.3 项目目标
1. 统一记录房间、入住、退房、换房和清洁任务。
2. 让前台与客房部查看同一份最新业务数据。
3. 退房后自动创建相应的清洁任务，减少人工传话。
4. 在清洁流程满足酒店要求后，才允许房间恢复为可入住状态。
5. 关键业务操作可追溯，发生错误时有记录可查。

### 1.4 第一版成功标准
- 前台能够完成一次正常入住、退房和换房。
- 退房后，系统会为原房间创建清洁任务。
- 客房服务员能够查看任务、开始清洁并提交完成结果。
- 前台与客房部能获取一致的房间状态。
- 同一间房不能因为两人同时操作而被成功分配给两个冲突的入住记录。
- 重要操作能查询到操作人、时间和结果。

【注释】“成功标准”是验收时用来判断系统是否达到目标的检查项，而不是视觉设计要求。

## 2. 用户角色

### 2.1 管理员
主要任务：创建员工账号、维护房间与房型资料、管理系统基础设置。

### 2.2 前台员工
主要任务：查看房态、办理入住、办理退房、办理换房、查看客人相关入住记录、记录异常。

### 2.3 客房服务员
主要任务：仅查看已分配给自己的清洁任务、开始清洁、提交清洁结果、报告房间异常。

### 2.4 客房主管
主要任务：查看所有清洁任务、分配或改派尚未开始的任务、在执行人无法继续时受控接管清洁中任务、人工创建清洁任务、处理异常。第一版不开发主管验收和退回整改流程。

### 2.5 酒店总经理
主要任务：查看并处理前台与客房部的日常业务，包括查看房态、办理入住/退房/换房、处理已分配清洁任务、分配尚未开始的任务、受控接管清洁中任务、人工创建任务、查看和解决异常、查询相关业务历史。

权限边界：酒店总经理的角色默认不等于“系统管理员”。除非另外被明确授予管理员权限，否则不能自动管理员工账号、分配角色、维护房型/房间基础资料或修改系统安全设置。第二阶段的额外服务价目表维护也应单独授权，不应因总经理可以使用前台和客房功能而自动开放。

【注释】可以把酒店总经理理解为同时拥有“前台业务权限”和“客房业务权限”的角色，但不自动拥有系统所有权限。后端需要真正授予这些权限，而不只是让总经理页面显示所有按钮。

### 2.6 第一版默认权限边界

第一版使用五个固定角色，支持一人多个角色；角色对应的具体权限由后端统一配置，不开发自定义角色或可视化权限编辑器。

| 操作 | 默认允许角色 |
|---|---|
| 查看房态、房型和必要房间详情 | 全部五类角色；按岗位裁剪详情 |
| 入住、退房、换房、查询必要住客与入住历史 | 前台、酒店总经理 |
| 查看本人任务、开始和完成自己的任务 | 客房服务员、客房主管、酒店总经理 |
| 查看全部任务、分配或改派待处理任务、人工创建任务 | 客房主管、酒店总经理 |
| 执行人无法继续时，受控接管清洁中任务并指定新执行人 | 客房主管、酒店总经理，必须填写原因并记录交接 |
| 上报及查看职责范围内异常 | 前台、客房服务员、客房主管、酒店总经理 |
| 确认异常解决、解除入住阻止 | 客房主管、酒店总经理 |
| 员工账号维护、给员工分配固定角色、房型和房间基础资料维护 | 管理员 |
| 查询关键操作记录 | 管理员查看管理记录；主管查看客房业务记录；总经理查看前台与客房业务记录 |

管理员默认不拥有入住、退房等业务办理权限，需要时追加相应业务角色。总经理不能为自己追加管理员角色。服务员不能通过修改任务 ID 操作他人任务；主管和总经理亲自清洁时，也需成为该任务的执行人。执行人因账号禁用、权限移除或其他原因无法继续时，按第 4.3 节受控接管，不绕过完成权限。普通客房查询不返回不必要的住客个人信息。

### 3.2 第二阶段：额外服务与收费（仅保留扩展参考）

第二阶段再支持点餐、果盘、加床、加被等额外消费，使用“服务项目目录 + 入住期间的服务订单 + 账单与收款”的方式管理。以下规则不属于第一版开发或验收要求，具体计价规则在第二阶段开始前确认。

- 管理员维护服务项目名称、类别、单位、价格、是否启用，以及必要的说明。例如“果盘”按份计价，“加床”可以按次或按晚计价，“加被”可按件计价。具体计价单位由酒店确认。
- 有权限的员工为当前入住记录登记服务项目、数量、备注。服务记录关联本次入住及发生时的房间使用记录，而不能只关联房号，因为同一房间会接待不同客人。
- 服务被实际提供后，员工将订单标记为“已完成/已提供”；取消的服务不能被计入最终应收金额。是否允许先登记、后确认，可按酒店流程调整。
- 创建服务订单时，应保存当时的项目名称、单价、数量和金额快照。管理员以后修改目录价格，不得改变已经产生的历史订单金额。
- 第二阶段结算页面展示房费、额外服务费、已收金额、优惠/调整（若启用）和应收金额。可先记录支付方式、支付金额、支付时间和经办人，不默认接入真实支付平台。
- 结算前允许前台核对明细；已结算的账单不应被普通员工随意改写。如需纠错，应留下调整记录和经办人。

【注释】“服务项目目录”类似价格菜单；“服务订单”记录某位客人这次实际点了什么；“账单”将本次入住期间应收费的项目汇总起来。这三者分开保存，才能防止以后改价影响历史消费。

## 4. 核心业务流程

### 4.1 办理入住
1. 前台打开“办理入住”。
2. 输入必要的住客信息和入住信息。
3. 系统只显示符合入住条件的房间供选择。
4. 前台确认提交。
5. 后端再次检查房间是否仍可分配。
6. 系统在一个事务中建立入住记录和第一段房间使用记录，并保存成功操作记录。
7. 页面提示成功或解释失败原因。

【注释】即使页面已经显示“空闲”，提交时也必须由后端重新检查，因为另一名前台员工可能同时操作了该房间。

第一版一次入住同时只使用一间房，可以多次换房。当前房间来自尚未结束的房间使用记录。预计退房时间由前台填写，实际入住时间由服务器生成；预计时间到达后不自动退房、不自动释放房间。

### 4.2 办理退房
1. 前台找到当前入住记录。
2. 核对住客与房间，提交当前房间使用记录 ID 并确认退房；后端核对其仍是当前段。
3. 系统用服务器时间记录实际退房，结束当前入住和当前房间使用记录。
4. 系统将房间标记为待清洁，并创建关联该房间使用记录的退房清洁任务。
5. 客房部看到新任务。

要求：结束入住、结束房间使用、标记待清洁、创建任务和成功操作记录必须在同一个数据库事务中完成；任一步失败则全部回滚。重复请求不能再创建任务。第一版不做财务结算，也不要求提供结算结果。

### 4.3 清洁任务
1. 服务员仅查看自己的任务；主管和总经理查看全部任务，并可通过人员分房页面批量安排。ADMIN 和前台不获得分配/改派权限。
2. 主管或总经理可分配、改派尚未开始的任务，执行人必须是启用且有清洁执行权限的员工。
3. 未分配任务由主管/总经理分配，支持选择员工、多选房间、一次确认；合法 DIRTY 空房没有任务时在同批事务中自动建单。负责人另行开始打扫，进入 IN_PROGRESS。所有角色自主领取关闭。
4. 执行人提交完成，记录完成时间，任务变为已完成，房间清洁状态变为清洁合格。
5. 后端重新计算房间是否可入住；仍有异常阻止或档案停用时，不恢复为可入住。

任务状态固定为 `PENDING → IN_PROGRESS → COMPLETED`，第一版不设主管审批、验收开关或普通清洁中改派。主管并发分房只能一方成功，整批成功或全部回滚。任务及房间状态、任务历史的变化应在同一个事务中完成，旧任务或重复完成不能覆盖新的清洁状态。

**执行人无法继续时的受控接管：** 原执行人账号禁用、失去清洁执行权限，或由主管/总经理确认因其他原因无法继续时，仅主管或总经理可发起接管，填写非空原因，并指定另一名启用且有清洁执行权限的员工，也可指定自己。接管需核对当前执行人未变，保留原开始时间和交接历史；任务仍为 `IN_PROGRESS`，房间仍为 `CLEANING`，不自动完成或恢复可入住。交接记录保存原执行人、新执行人、操作人、原因和服务器时间。接管后仅新执行人可提交完成，原执行人即使恢复账号也不能再完成该任务。接管与完成并发时按同一锁定规则处理，不能互相覆盖。未分配待处理任务走首次分配；已经分配的待处理任务走带原因的重新分配。第五阶段将待处理改派与清洁中接管统一为重新分配接口，按当前状态分别校验。

主管和总经理可为无人入住、已经 DIRTY 且无未完成清洁任务的房间人工创建任务，用于初次或必要的待清洁任务；创建不任意改动房态。同一房间最多存在一个未完成清洁任务，同一段房间使用记录只能生成一个离房清洁任务。

### 4.4 办理换房（第7阶段已实现）

1. 前台或总经理选择当前有效入住，提交当前使用段ID、符合统一可入住条件的目标房、换房原因类型及必填说明。
2. 原因 GUEST_REQUEST/ROOM_ISSUE/OTHER。ROOM_ISSUE可选关联真实原房异常；不要求所有故障换房先创建异常，提供关联时须匹配原房。最新指令替代原强制关联严重异常草案。
3. 同事务关闭原段、建立新段、保存换房事实、原房DIRTY并创建唯一换房清洁任务、保存成功审计及幂等结果。服务器统一换房时间，历史完整保留。
4. 入住ID、全部住客、实际入住和预计退房时间不变，目标房继续入住；原房异常/维修记录不变，换房失败也不删除此前异常。
5. 允许跨房型、多次换房；最终退房使用最后有效段。入住→房间ID升序→使用段的行锁、旧段核对及24小时幂等保护避免重复分配和退房冲突。任何关键写入失败全回滚。

实际接口与页面见 [ROOM-CHANGES.md](ROOM-CHANGES.md)，没有差价、收费、自动换房、住客名单变化或额外占用数据表。

### 4.5 房间异常与维修停用（第 6 阶段已实现）

前台、客房服务员、主管和总经理可上报；服务员仅查看自己提交的异常，前台及主管可查看全部。类型与程度独立：FACILITY/ELECTRICAL/PLUMBING/SANITATION/SAFETY/OTHER；LOW/MEDIUM/CRITICAL。未解决 CRITICAL 自动阻止新入住，普通异常由主管按需要另设人工维修停用。

异常 OPEN → IN_PROGRESS → RESOLVED，主管和总经理可带结论直接解决 OPEN；调级须版本和原因，历史完整保留。维修停用和恢复仅这两个角色可做，ADMIN 不拥有客房业务权限。

维修状态由“未解决严重异常或有效人工停用”统一计算，任何一个仍存在都会阻止入住；解除人工停用前必须解决严重异常。清洁完成不解除停用，解决异常不自动清洁或关闭独立停用。已入住房间可上报但绝不自动退房/换房。

上报、处理、停用和恢复使用同一房间锁及24小时幂等机制，成功历史、审计、结果同事务。完整接口、权限和操作规则见 [ROOM-ISSUES.md](ROOM-ISSUES.md)。此规则取代早期按 EQUIPMENT_FAILURE/HYGIENE_ISSUE 类型控制 blocksCheckIn 的草案。

### 4.6 登记额外服务（第二阶段参考，第一版不实现）
1. 前台（或被授权员工）打开客人当前的入住记录，选择“新增额外服务”。
2. 从管理员维护的服务项目中选择，例如餐食、果盘、加床或加被。
3. 填写数量、计价单位和必要备注；系统展示当前单价及小计。
4. 系统保存服务项目名称和价格快照，并关联当前入住及服务发生时的房间使用记录。
5. 服务完成后，员工将其标记为“已提供/已完成”；取消的服务应记录取消原因，不计入应收金额。
6. 前台可以查看本次入住的服务消费清单。

【注释】请避免只把消费挂在“801 房”上。客人退房后，801 房还会分配给别人；消费应关联到“某一次入住”，这样账单不会串到下一位客人。

### 4.7 退房结算（第二阶段参考，第一版不实现）
1. 前台打开当前入住记录的结算页面。
2. 系统汇总本次入住的房费（按第二阶段确认的计价规则计算）和已提供且应收费的额外服务。
3. 页面逐项展示费用明细、总额、已收金额和待收金额；前台核对后确认结算。
4. 记录结算金额、支付方式、支付时间和经办人。第二阶段可先记录人工收款结果，不默认接入真实支付平台。
5. 已结算账单如需更正，应通过有记录的调整操作完成，而不是直接覆盖历史金额。

【注释】第二阶段再确认按日房价、押金、折扣、税费、退款以及退房与结算的先后关系。第一版不自动猜测或计算任何费用。

## 5. 房间状态与业务规则

### 5.1 第一版房态及判断依据
- **空闲可入住**：无住客、清洁合格、无阻止入住的故障或占用冲突。
- **已入住**：存在有效入住记录。
- **待打扫**：需要清洁，尚未开始。
- **正在打扫**：清洁任务已开始。
- **维修停用**：暂时不能安排入住。
- **档案停用**：管理员停用房间基础资料，不参与新分房。

占用来自未结束的房间使用记录；清洁状态独立保存为 `DIRTY / CLEANING / CLEAN / INSPECTION`；维修阻止来自未解决 CRITICAL 异常或有效人工维修停用；档案启用来自房间资料。新建房间默认待清洁，需创建并完成清洁任务后才能分房。

**可入住 = 档案启用 + 无当前占用 + 清洁合格 + 无未解除的入住阻止 + 无未完成清洁任务。** 后端统一提供此判断，查询、入住、换房使用同一规则。

主要展示状态按“档案停用 → 已入住 → 维修停用 → 正在打扫 → 待检查 → 待打扫 → 暂不可分配 → 空闲可入住”判断，同时返回异常、清洁等标记。例如“已入住 + 空调故障”不能丢失任一事实。第一版不提供直接任意修改综合房态的功能，不展示已预订状态。2026-10-20 已确认：支持待检查状态的数据与展示，不开发检查/验收流程，也不自动进入该状态；暂不可分配用于清洁合格但仍有未完成任务等情况。当前第 2 阶段的事实来源及测试边界见 ROOMS.md。

### 5.2 关键规则
1. 同一时间不能有相互冲突的有效入住记录占用同一房间。
2. 只有满足入住条件的房间才能分配给客人。
3. 退房成功后应创建清洁任务。
4. 清洁未按规定完成前，房间不能恢复为可入住。
5. 维修停用的房间不能办理入住。
6. 换房必须保存历史记录。
7. 重复点击或重复提交不能生成重复的退房记录或清洁任务。
8. 关键操作必须检查权限并留下操作记录。
9. 实际入住、退房、换房、任务操作、异常上报及处理时间由服务器生成；预计退房时间由前台填写。第一版不支持历史补录。数据库事件时间统一用 `TIMESTAMPTZ`，接口用带时区的 ISO 8601，默认按 `Asia/Shanghai` 显示。
10. 入住、退房、换房、任务分配和异常阻止变化必须协调并发访问，不能只依赖页面按钮禁用。
11. 关键业务历史不提供普通删除接口；被引用的员工、房型和房间优先停用，不级联删除历史。房间存在当前占用或未完成清洁任务时，不允许档案停用。停用房型仅禁止新增或改绑房间选择该房型，不自动停用已引用房间或结束入住。
12. 页面操作成功后刷新数据，房态页支持定时查询与手动刷新；第一版不要求 WebSocket。页面数据不是分房依据，提交时后端再次检查。

## 10. 常见词汇解释

- **房态**：房间当前处于什么业务状态，例如已入住、待打扫、空闲可入住。
- **业务闭环**：一个流程从发起到完成，相关记录和状态都正确更新。
- **后端**：运行在服务器上、负责业务规则和数据处理的程序。
- **前端**：员工通过浏览器看到并操作的页面。
- **接口/API**：前端与后端交换数据、提交操作的约定入口。
- **事务**：把一组相关数据库操作作为一个整体处理，避免只完成一半。
- **幂等**：同一操作因为重试而被提交多次，结果仍不会重复创建业务数据。
- **价格快照**：把下单那一刻的服务名称、单价和金额保存到订单中；以后目录价格变化，历史订单仍保持原金额。
- **结算/账单**：把一次入住期间需要支付的房费和其他消费汇总，供前台核对并记录收款结果。
