- 状态：V1.0、V1.1 与 V1.2 均已本地验收；最新 V1.2 为 356 项 JUnit、153 项真实浏览器及前后端构建/打包通过，见 [V1.2 交付记录](releases/V1.2-DELIVERY.md)。下一主线为 V1.3 非财务交班；V1.3 及以后未在本次实施，规划不替代实施授权。真实上线条件仍见发布清单。

## 一、核心判断

StayOS 当前已经是一套比较完整的“店内房态与客房协同系统”，但还不是可以替代所有前台、预订和收银工作的完整 PMS。

第一版最值得补的不是会员、OTA 或大数据看板，而是两类工作：

1. **上线收口**：把现有测试、安全、部署、备份恢复、身份核验及日常故障处理流程真正落地。
2. **高频前台补缺**：按 V1.1 续住、V1.2 资料笔误更正、V1.3 非财务交班逐项交付；入住确认单打印按需加入 V1.3。住中清洁作为 V1.4 条件版本，不能把当前离房清洁直接复用于仍在住房间。

房费、账单、押金、收退款属于下一产品大版本，不建议以“轻量补功能”为名偷偷塞回 V1。保持仓库既定的“第二阶段做收费”约定：先完善 V1 的店内闭环，再做 V2 账务、V3 预订、V4 渠道。会员和多门店不应成为这条主线的前置条件。

如果 V1 先用于真实试运行，必须明确：预订、收费、开票等工作仍由酒店原有合规流程或既有系统承担，并规定数据核对和操作责任，不能让两套系统各自独立决定可售库存或把 StayOS 的“已退房”当成“已结清”。

## 四、第一版到底还缺什么

### 4.1 V1.0 正式试运行前必须收口的项目

这些不是再加一个大模块，而是把现有能力交付完整：

1. **验证当前工作树（本地已完成）**：2026-10-31 第五批全量 JUnit 284 项、Playwright 130 项及前后端构建通过，覆盖五角色、账号撤销、幂等、并发、数据库故障和退出降级；之后代码变化仍需对应回归。本地通过不自动完成以下现场事项。
2. **真实部署核对**：HTTPS、Secure Cookie、反向代理来源配置、受限数据库账号和生产密钥校验在目标环境实际跑通，不能只依赖本地测试。
3. **备份和恢复演练**：落实离机副本、密钥独立保管、定时备份及失败告警；在隔离环境恢复成功，并明确可接受的数据损失与恢复时间目标。
4. **真实酒店操作规程**：新房先清洁、退房无收款含义、故障不由清洁自动解除、误操作不能私改数据库；准备断网/停机时的人工登记与事后核对流程。
5. **上线前置确认**：属地实名核验/住宿登记报送、个人信息处理依据和留存期限、员工访问范围及清理方式。确有法定或经营要求的流程必须在上线前满足，可以使用酒店现有合规系统，不一定全部由 StayOS 内置实现。

门禁、身份证阅读器、公安报送、税务开票是否需要由 StayOS 直连，应根据当地要求和现有系统决定；既不能统一承诺“都不用”，也不能无依据要求“全国都必须通过某一种设备/接口”。

### 4.2 最值得逐步进入 V1.x 的业务补缺

#### A. V1.1：在住续住和预计离店时间调整

- 不通过“先退房再入住”模拟续住，否则会错误触发清洁并切断原入住历史。
- 只允许有权岗位操作在住单，记录原时间、新时间、原因、操作人和版本。
- 更新运营待办；重复提交不重复产生记录，并发退房/换房时有明确结果。
- V1.1 不产生房费，也不声称已收续住款；V2 对接房费，V3 再增加未来预订冲突校验。

#### B. V1.2：住客资料受控更正

- 先限定为录入笔误更正，不默认允许换人、合并客历或随意增减同住人。
- 保留变更轨迹，维持密文保存和掩码展示；审计日志不能记录明文证件和电话。
- 更正与历史快照的保留方式需设计，不能简单开放任意历史表编辑。
- 如涉及住宿登记信息变更，应与酒店现有核验/报送流程衔接。

#### C. V1.3：非财务业务交班

- 复用现有待办生成交班时点摘要，增加交班人备注、未完成事项、接班人确认及时间。
- 区分“交班时的快照”和“现在的实时状态”，事后变化不能覆盖已确认的交班记录。
- 不涉及现金、押金、营业收入，也不是重复做运营待办看板。

#### D. V1.3 可选：按需打印入住确认单

- 先确定是否需要纸面签字及纸张规格，再做一个受控模板和打印入口。
- 默认脱敏；普通业务确认单/收据不等于法定发票。
- 打印及导出不作为增加明文敏感资料访问权的理由。

#### E. V1.4 条件版本：住中清洁与服务请求

- 当前 `TaskWorkflowService` 的人工创建、开始与完成均要求房间无人入住；这是现有离房清洁规则，不能只删除 occupied 校验来支持住中清洁。
- 若酒店要求每日打扫，单独增加住中服务任务，支持清洁、更换布草等明确类别，以及请勿打扰、拒绝、稍后服务和未完成原因。
- 任务关联当前入住及房间使用段，退房/换房时按规则关闭或重建，不能串给下一位住客。
- 完成住中服务不结束入住、不释放房间、不把仍占用的房间标成可售；与离房清洁保留不同状态含义。
- 先明确真实需求；若目前只需离房清洁，可跳过此版直接进入 V2。

误退房恢复、同住人增减、完整号码检索不是上述工作的顺带小改动。V1 先制定申请、核查和人工处置规程；若试用证实必须开发，单独定义补偿事件、权限及不可恢复条件，再安排小版本，不开放万能“撤销”按钮。

## 六、各版最低验收标准与范围控制

### V1.0：可靠地交付已有能力

- 五岗位真实操作走通“清洁 → 入住 → 异常/换房 → 原房清洁 → 退房 → 清洁 → 再次入住”。
- 操作人被停用/撤权、重复请求、并发请求、数据库故障不会产生半条业务或越权成功。
- 目标部署环境可诊断、可备份、可隔离恢复；故障时有业务兜底。
- 上线清单中的阻止项关闭后，才进入真实资料试运行。开发环境验收不代替这一步。

### V1.1～V1.4：每次只增加一个操作闭环

- 续住不新建入住单、不生成退房清洁任务；预计离店提醒随之变化。
- 更正不会泄露明文资料，原变更轨迹可追溯；无权岗位不能操作。
- 交班记录可查询接班确认；未确认不能假装已完成交接。
- V1.1、V1.2、V1.3 分别发布和回归；V1.4 仅在酒店需要住中服务时启动。各版会扩展原 V1 排除范围，实施前先确定相应规则。
- 住中服务完成后，入住和房间占用不变；并发换房/退房不会把服务任务留给下一位住客。

### V2.0：建立轻量客账，不做支付公司

主要内容：

1. 房型基础价、实际入住价格快照、按营业日的房费明细；先选一种明确的计费规则，钟点房和复杂套餐后置。
2. 每次入住对应轻量客账，支持房费及额外服务/商品费用；先记录消费，不附带完整进销存。
3. 押金/预收、现金及外部已完成的微信/支付宝收付款人工登记，保存方式、金额、经办人和可核对的外部流水参考。
4. 部分付款、退还押金、费用减免和差错冲正；原流水保留，不用删除/覆盖表示退款。
5. 结账明细和普通收据。应收、资金流水、未结余额分别展示。

关键边界：

- 押金/预收不是营业收入；一次收款不能同时被算成押金和收入两遍。
- 金额使用精确十进制或最小货币单位，不使用浮点数算账。
- 先定义营业日、入住/离店计费边界、换房差价、提前退房、续住及减免规则。
- “人工登记已支付”不等于系统发起或验证了真实支付；界面必须表达清楚。
- 入住状态、客账状态、支付交易状态分开。是否允许带账退房由酒店确认，不擅自把 V1 的退房接口改成必须结清。
- V1 历史入住没有原始价格和收款事实，不追溯凭空生成应收，也不强行视为零元交易。

验收示例：2 晚每晚 200 元，加服务费 30 元，应收 430 元；外部实收并登记预收 500 元，外部退回并登记 70 元，最终净实收 430 元、余额为零。重复点击不重复入账，退款受额度限制，冲正后原记录仍可追溯。该示例仅验证记账，不代表系统已经实际扣款或退款。

### V2.1：把收银与经营数据核对清楚

主要内容：

- 收银班次、备用金和现金盘点、各收款方式的本班汇总、交接双方确认。
- 房费入账及营业日关账；采用可重试且幂等的任务，先人工触发/核对，再考虑自动化夜审。
- 操作待办交班与收银交班有关联但不混为一个状态。
- 入住/离店、房晚、入住率、房费、其他消费、收退款、欠费基础报表；有可靠数据后再算 ADR/RevPAR。
- 受控费用更正和关账后调整；业务误操作恢复若立项，单独采用补偿流程和风险校验，不允许直接回滚所有历史。

验收标准：

- 班次收退款汇总与流水一致，账面现金与实盘差异可说明且不靠改金额“抹平”。
- 报表区分收入、收款、押金和退款，关账后原日报不被静默重写。
- 入住率等指标写明营业日、可售房分母和维修停用口径；新上线前没有的数据不伪造历史。

### V3.0：预订与未来库存

主要内容：

1. 预订编号、来源、到离店日期、人数、房型、价格快照和联系人；先从一单一房或清晰限定的简单场景开始。
2. 按房型/日期管理可售量，具体房号可稍后分配；预订事实与实际房间使用段保持独立。
3. 预订日历、排房、预订转入住、取消、未到店、到店日期/房型变更。
4. 占用名额的状态、保留期限和释放条件；预订预付款复用 V2，取消收费规则另外确认。
5. 未来维修/停售日期、续住与未来预订冲突处理。

范围控制：

- 前台可手工录入电话、线下和 OTA 订单，并保存外部单号；此时不声称已经自动与 OTA 对账或同步。
- 默认禁止超卖；V1.1 的续住不能继续只看“当前空闲”，要升级为未来区间冲突检查。
- 大团房块、跨日拆分多房订单、复杂连住促销及会务后置。
- 日历只是库存逻辑的展示层，不是先画一个页面就完成了预订系统。

验收标准：同日期最后一个房型名额被两名员工并发预订时只成功一笔；取消和保留超时按规则释放；预订转入住不重复扣库存；已有未来预订时不能无条件续住侵占其名额。

### V4.0：先接好一个外部渠道

主要内容：

- 先确认渠道商务授权、技术资质、凭据和可用测试环境，必要时接成熟渠道管理服务而不是逐个平台硬接。
- 一个渠道的订单接收、变更和取消；房型/房价计划映射；库存及必要价格同步。
- 外部单号唯一、回调认证、幂等、乱序/重复消息处理、失败重试和人工异常队列。
- 定时核对外部订单与本地事实，展示同步时间与错误，不把“接口返回成功”当永久一致。
- 连接中断或对账不一致时有停售/人工接管规程，再逐个扩展渠道。

验收标准：重复或乱序回调不创建重复入住/预订，不因超时盲目重复扣款；差异可定位并可人工处理；外部同步失败不会破坏店内现有入住与清洁功能。

后续小版本：官网或小程序订房、验证码/消息通知、正规支付网关、退款回调及对账。采用支付机构托管页面或令牌化能力，不自行收集保存银行卡敏感信息。

iCal 可在相应渠道支持时作为辅助日历交换，但通常不能替代实时双向订单、价格、付款及库存同步，不承诺“接了 iCal 就能防超卖”。

### V5.0：从真实经营问题中选精细化能力

优先从下列候选中选择，而不是整包一次开发：

- 客人同意及适当权限下的有限客历、偏好、复住识别；不能仅因保存过证件就自动形成营销画像。
- 协议公司、协议价及受控挂账，或简单会员价；避免初期同时引入积分、储值和复杂权益。
- 有可靠账务、预订和渠道数据后的客户/渠道经营分析。
- 若客房部确有需要，再加查房验收、周期维修、遗失物品或物料库存；这些不是当前清洁闭环的当然缺陷。

验收标准：至少明确解决一个实际问题，例如协议客户结算困难、复住识别或渠道利润不清；数据访问、合并和留存有规则。没有经营需求则不进入该版本。

### V6.0：有第二门店再做多店

- 门店数据隔离、跨店角色与总部权限、按门店编号和配置、汇总报表。
- 跨店客历、资金和库存共享是另外的业务决策，不默认共用。
- 上线前验证越店访问、门店迁移及汇总口径；不因做多店就自动拆微服务。

只有实际出现第二家店或明确的多客户 SaaS 目标才启动。若长期单店，本版本可以永远不做。

## 七、跨版本必须守住的设计原则

1. **四类核心事实分离**：预订、实际入住/房间使用段、客账、支付交易各自有生命周期，通过关联和事件协作，不用一个万能订单状态代替全部。
2. **保持房态可用性规则**：清洁、维修、实际占用和未来库存各负其责。不能为了对接渠道而允许任意写一个 `available=true`。
3. **新增事实不抹历史**：财务用冲正/退款，业务恢复用受控补偿；旧房间使用段、任务历史和审计不因“撤销”而删除。
4. **敏感数据最小化**：客资更正、打印、搜索、导出和客历建设都要有权限与留存设计；不为了搜索而存完整明文号码。
5. **沿用现有单体架构**：优先按业务包加模块。暂不引入微服务、复杂消息中间件、AI 定价或原生移动 App 来替代具体需求。
6. **迁移兼容**：新增迁移，不篡改已应用的 Flyway 历史；兼容 V1 旧入住单和现有幂等约定。
7. **按小闭环发布**：每项具备界面、接口、权限、数据约束、审计、失败处理、自动化测试和操作说明，再进入下一项。

## 八、最近应该怎么做

### 推荐顺序

以下顺序沿用已认可的大版本路线；V1.0 和 V1.1 已本地验收，后续版本仍按明确授权实施。

1. V1.0/V1.1 本地回归已通过，按发布清单完成目标环境与酒店试运行准备；保留当前未提交改动及各批证据。
2. 下一开发版是 V1.2 更正，之后 V1.3 交班；V1.1 续住不重做。打印按需加入，V1.4 住中服务由酒店实际需要决定，未启用前不改现有清洁规则。
3. 在不提前开发收费的前提下，整理 V2 的房费、押金、退款、离店及营业日规则，再进入 V2.0。
4. 账务稳定后做 V2.1 和 V3；有外部授权与可维护能力后再进入 V4。
5. 以后每版基于试用反馈重新排序，而不是为了凑齐竞品清单强行进入 V5/V6。

### 实施前需要确认的决策

- StayOS 是先辅助现有 PMS，还是目标最终替代？现有预订/账务/住宿登记分别由谁负责，哪个系统对哪类数据负责？
- 酒店的退房时间、按天/钟点计费、提前退房、续住及换房差价规则是什么？
- 资料更正由谁批准？更正、换人和增加同住人如何区分？是否需要纸质确认单？
- 交班是单方提交还是双方确认？非财务事项与现金交接分别由谁负责？
- 押金、挂账、欠费离店、折扣、冲正、退款的权限和额度如何确定？先只人工登记收付是否可行？
- 上线所在地对身份核验、住宿登记、隐私留存和税务开票的要求，以及现有合规工具是什么？

本次不预设开发周数或固定发布日期：尚无团队人数、投入时长和现场试用条件。按功能闭环和验收门槛划版，比给出无依据的工期更可靠。
