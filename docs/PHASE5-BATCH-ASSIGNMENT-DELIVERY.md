日期：2026-10-20，上海时间。本次是第五阶段完善，保留原未提交代码，不创建新开发阶段，不自动暂存或提交 Git。原第五阶段验收快照见 [PHASE5-DELIVERY.md](PHASE5-DELIVERY.md)，当前业务与接口见 [HOUSEKEEPING.md](docs/HOUSEKEEPING.md)。

## 1. 实际操作流程

1. 客房主管或酒店总经理登录，从导航进入 [人员分房](http://127.0.0.1:5173/housekeeping/assignment)。
2. 员工卡片显示真实姓名、账号/编号、启用状态、待开始数量、清洁中数量、上海自然日今日完成数量。仅显示启用且有清洁执行资格的人员。
3. 点击员工，左侧显示其全部未完成房间，包含房号、楼层、房型、任务来源、状态、分配/开始时间及详情历史。
4. 右侧按楼层、房型、房号筛选，勾选多间房；可逐间取消、清空或全选当前筛选可分配房间。全选跨分页，超过 100 间要求缩小范围，保留原选择。
5. 页面显示已选数量和房号。确认窗口显示目标员工、房间数量、完整房号及选填非敏感备注，点击一次“确认本批分房”，发送一次批量请求。
6. 成功后自动重新查询员工工作量、员工当前任务与房间状态，清空选择。房间负责人已变，但任务仍为 PENDING，员工正式开始后才进入 CLEANING。

房间按楼层与房号数字片段自然排序，例如 A2 在 A10 前。界面以文字区分可分配（已有任务/自动建单）、已分配给此员工/其他员工、正在打扫、已清洁、已入住和状态不符。停用/维修提示独立显示，沿用原规则允许空闲 DIRTY 房间清洁，但不会解除停用或入住阻止。

服务员仍使用 [清洁任务工作台](http://127.0.0.1:5173/housekeeping/tasks)，只查看本人任务、开始/完成及本人任务历史。单间人工创建、主管单条分配和带原因重新分配继续保留。

## 3. 两种任务来源

- 已有合法、未分配 PENDING 任务：锁定后直接分配原任务。任务 ID、CHECKOUT/MANUAL 来源、入住及房间使用段关联保持原值，不创建第二条未完成任务。
- 没有未完成任务：确认真实房间、无人占用、DIRTY 后，同事务创建 MANUAL/MANUAL_CLEANING，真实创建人、服务器时间和必要原因，再直接分配。入住/退房/使用段关联均为空。
- 未填备注时，人工创建原因使用“人员分房：初始客房清洁”；填写备注时按已有 1000 字与控制字符校验保存。界面提示只填清洁安排，不收集住客资料。
- 已分配、IN_PROGRESS、已入住、CLEAN、INSPECTION 或状态不符均拒绝普通批量分配，不静默抢占。调整已有负责人仍使用原因必填、版本校验的 reassign。

新增 `backend/src/main/resources/db/migration/V10__housekeeping_batch_assignment.sql`。V1—V9 保持原内容，不清空数据库。

| 变更 | 用途 |
|---|---|
| housekeeping_assignment_batches | 批次 ID、操作人、目标员工、服务器时间、必要备注 |
| housekeeping_assignment_items | 每房对应原任务、房号快照、可选人工创建日志、必填分配日志 |
| idempotency_requests.result_assignment_batch_id | 原请求机制的批次结果关联 |
| 操作/结果类型约束 | 新增 HK_BATCH_ASSIGN，入住、单任务、批次结果字段互斥 |
| 条目复合外键与唯一约束 | 房间必须对应任务，日志必须对应任务；批次内房间/任务唯一，分配日志唯一 |

批次表用于记录多房分配结果，清洁任务仍由原 housekeeping_tasks 唯一管理。原同一房间最多一条 PENDING/IN_PROGRESS 的部分唯一索引继续生效。

事务顺序：

请求预留 → 操作人/员工按 ID 升序共享锁 → 全部房间按内部 ID 升序行锁 → 逐房重查、锁任务、必要时建单 → 分配、每任务历史、成功审计、批次条目 → 幂等结果 → 一起提交。

一次选择 10 间，即使最后一间冲突，之前的任务创建、分配、历史、审计、批次和请求预留全部撤回。原任务原负责人不会被覆盖。用户共享锁保护资格校验，房间锁顺序与原入住/退房/清洁兼容，任务更新仍检查当前版本。清洁流程不反向锁入住记录。

## 5. 幂等和不确定结果

沿用原 PostgreSQL IdempotencyService、HMAC 摘要和 24 小时规则，扩展同一结果关联结构。

- 摘要使用目标员工、升序房间 ID 集合及去两端空白的备注；原请求换数组顺序仍返回同一成功结果。
- 相同标识更换员工、房间集合或备注拒绝；超过 24 小时的旧标识拒绝重新执行，最小记录保留。
- 失败整体回滚，修复后原标识可安全重试；并发相同请求最终只建一个批次和一组历史。
- 回执保存房号快照；以后修改房号也不会改变原分房结果。幂等表只保存摘要和关联 ID，不保存完整请求或住客资料。
- 提交期间禁止重复点击；响应丢失/损坏保留原标识和内存请求。sessionStorage 仅保存标识、员工/房间 ID，不保存备注或完整请求。
- 刷新后可以按当前操作人＋原标识查询成功批次，不自动发新请求。暂未查到成功结果不等于在途请求已取消，界面明确提示继续查询或原标识重试。
- “核对后结束重试”只清本机提示，需要明确确认，不撤销成功业务。

## 11. 用简单的话理解

- **批量事务**：一次分房是一个整体，不能分一半留一半；任一步失败全退回。
- **按顺序加锁**：多人碰到同一房时排队检查，多房统一按 ID 顺序，减少互相等锁。
- **权限与范围**：主管能分房，服务员只能干分给自己的活；服务器检查，隐藏按钮只是界面提示。
- **幂等**：网络不好重复点原请求，系统认出这是同一次分房，不会重复建单或重复写历史。
- **历史和批次**：批次说明“这一次分了哪些房”，任务历史说明“每一间由谁分给谁、什么时候开始和完成”，两者都保留。
- **增量迁移**：新增 V10 记录结构变化，已运行的 V1—V9 保持原样，已有数据顺序升级。
